# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A personal finance tracker ("Quản lý tài chính cá nhân") built as Python + SQLite, usable from either a terminal CLI or a Flask web form. The project follows the 7-stage roadmap in [docs/THIET-KE.md](docs/THIET-KE.md) (Vietnamese design doc — read it before making schema or product-behavior decisions, it is the authoritative spec). **Stage 1** and **Stage 2** (auto-categorization, recurring transactions, learn-a-rule-from-correction) are fully built. **Stage 6** (Part 4's risk metrics, Part 1.3's proactive alerts, Part 3.7's income sources, and Part 3.8's event planning) and the **Stage 4** screenshot import are also built, all picked up out of roadmap order, deliberately: risk metrics and alerts needed no external data; income sources and event planning were requested directly, inspired by looking at MoMo/Timo's own features (see memory `project_stage2_progress`); screenshot import (`/import` in the web app, [src/ocr_import.py](src/ocr_import.py)) is now powered by the Gemini API's image understanding rather than local OCR, after local Tesseract's accuracy on real screenshots proved hard to fix with regex (see the file's own module docstring and CLAUDE.md's Architecture section for the full story). **Stage 3 (auto-reading MB Bank emails) was skipped, not just deferred** — the user found it's blocked by iOS email-access restrictions, so screenshot import (Stage 4) became the real path for semi-automated import instead. Not yet built: a nicer web UI (current one is deliberately plain), and Stage 7 (investments/gold/FX). `budgets` (category-level "Hũ chi tiêu" budgeting) also isn't in THIET-KE.md at all — added by direct request, inspired by Timo, not part of the original design.

`init_db.py`, `seed_data.py`, `transaction.py`, and `risk.py` use only the Python standard library. `web_app.py` needs Flask, and `ocr_import.py` needs `google-genai` + `pydantic` (both in `requirements.txt`) plus a `GEMINI_API_KEY` (get one free at [aistudio.google.com/apikey](https://aistudio.google.com/apikey)) — see Commands below.

## Commands

```bash
# One-time: install third-party Python dependencies (Flask, google-genai, pydantic)
pip3 install -r requirements.txt

# Create the database and tables from schema.sql (data/finance.db, gitignored)
python3 src/init_db.py

# Seed initial accounts and categories (safe to re-run: no-ops if categories already exist)
python3 src/seed_data.py

# Run the interactive terminal CLI (add transaction / list recent / monthly totals)
python3 src/transaction.py

# Run the web form instead (same feature as "add transaction" in the CLI, browser-based)
# APP_PASSWORD is required — the app raises RuntimeError at import time if it's unset.
# GEMINI_API_KEY is only needed for the /import (OCR) page — every other route works without it.
APP_PASSWORD=your_shared_password GEMINI_API_KEY=your_key python3 src/web_app.py
# Serves on http://0.0.0.0:8000 — reachable from other devices (e.g. a phone) on the same LAN.
# Port 8000, not 5000: macOS AirPlay Receiver squats on 5000 by default.
```

There is no test suite, linter, or build step configured yet.

To reset the database from scratch: delete `data/finance.db`, then re-run `init_db.py` followed by `seed_data.py`. **After pulling a change to `schema.sql`, re-run `python3 src/init_db.py` against your existing `data/finance.db`** — every statement in it is `CREATE TABLE IF NOT EXISTS`, so this only adds newly-introduced tables and never touches or drops existing data.

## Architecture

**Storage**: single SQLite file at `data/finance.db`, gitignored (per docs/THIET-KE.md, real financial data must never be committed). Every module resolves the project root as `Path(__file__).parent.parent` and connects with `PRAGMA foreign_keys = ON` and `row_factory = sqlite3.Row`.

**Schema** ([src/schema.sql](src/schema.sql)), defined and explained in full in docs/THIET-KE.md Part 3:
- `accounts` — one row per money store (bank, ewallet, credit_card, cash, savings). `is_liquid` flags whether it counts toward liquidity/emergency-fund calculations (e.g. credit card debt is not liquid).
- `categories` — self-referencing tree via `parent_id`. `kind` is expense/income/transfer. `necessity` (essential/optional) powers the risk metrics in `risk.py` (50/30/20 rule, "months of runway" if income stops — see below). `stability` (fixed/variable) is still unread by any code — don't drop it anyway, it's designed-in for later.
- `transactions` — the central table. `amount` is always positive; sign is carried separately in `direction` (in/out). `source` is `manual`/`recurring`/`ocr` in practice today (`email` is in the schema's CHECK constraint but has no writer — Stage 3 was skipped, see overview). `is_reviewed` exists for a not-yet-built *batch* review workflow; both `recurring`- and `ocr`-sourced transactions are inserted with `is_reviewed = 0` (manual entries are `1`) even though OCR imports already go through a review-and-edit screen at import time — that inline review is a per-batch safety step, not the same thing as the design doc's dedicated "chờ duyệt" screen, which still doesn't exist. `external_ref` is the dedupe key; OCR import is its first real user (see below).
- `behavior_events` — structure existed unwritten-to since Stage 1 by deliberate design (see THIET-KE.md Part 5: "tạo cấu trúc từ Giai đoạn 1, chỉ ghi dữ liệu thật từ Giai đoạn 2"). Now has two real writers: `category_overridden` (`log_behavior_event`, used when a transaction's category is edited) and `alert_shown` (`alerts.log_shown_alerts`, used when a risk warning is displayed — see below). Other event types (`transaction_reviewed`, `alert_acted_on`, etc.) still have no writer — don't add one before the feature that produces that event actually exists.
- `rules` — auto-categorization: `pattern` is matched case-insensitively as a substring of a transaction's `description`; on match, `category_id` is assigned and `hit_count` increments. Tried highest-`priority` first. `created_from` distinguishes rules added directly (`'user'`, via CLI menu option 4) from ones learned by correcting a transaction's category (`'learned'`, via CLI menu option 8 or the web's edit-transaction page).
- `recurring` — recurring transaction templates (rent, subscriptions, ...). `next_due` advances by `frequency` (monthly/quarterly/yearly) each time it fires; `day_of_period` is stored but not currently used to compute due dates (next_due is set explicitly and advanced from itself, not recalculated from day_of_period — don't assume it's authoritative). Added via CLI menu option 6 only.
- `income_sources` — THIET-KE.md 3.7: each row is one income stream (a teaching job, a scholarship, freelance work, ...) with an `expected_amount` and a `reliability` (0–100%). The point of keeping this separate from `transactions` income history is right there in the design doc: a side gig's *expected* amount shouldn't be treated as certain just because it's expected — `reliability` is what lets `risk.py` discount it. Added via CLI menu option 10 only.
- `budgets` — **not in THIET-KE.md**, added by request inspired by Timo's "Hũ chi tiêu" (envelope budgeting per-category — THIET-KE.md 7.3 itself notes this general method as "chưa triển khai" at design time). One row per category with an active `monthly_limit`; `set_budget()` upserts (one active budget per category — setting it again replaces the limit, it doesn't insert a confusing duplicate row).
- `event_templates` / `event_items` (THIET-KE.md 3.8): a template (Chuyển nhà, Cưới hỏi, Du lịch — seeded in `seed_data.py`'s `_seed_event_templates`, guarded by its own count check so it seeds independently even on a re-run where categories already exist) with suggested line items. **Item *names* only, never a suggested price** — that's the design doc's explicit principle (price depends on locale/circumstances, guessing it would be wrong and erode trust), strictly followed when picking Cưới hỏi/Du lịch's item lists too (well-known checklist items, not financial advice).
- `event_plans` / `event_plan_items` — a real plan the user builds, optionally from a template (`template_id` nullable — a plan can be fully custom). `event_plan_items` is **not explicitly named in THIET-KE.md** but is a necessary, directly-justified extension of it: the doc says `event_plans` should carry "expected vs. actual" amounts, and that only makes sense tracked per line item. `expected_amount` is user-entered per item when creating the plan (CLI menu 15, `create_event_plan_interactive`); `actual_amount` exists in the schema for the same reason but **has no CLI/web writer yet** — don't assume it's populated anywhere.
- Tables described in the design doc but still **not in schema.sql**: `income_sources`' sibling concept from Part 7 (theory background, not a table) and anything from later stages (email/OCR-adjacent, investments). When implementing a later stage, add tables incrementally rather than scaffolding them all up front.

**Auto-categorization and recurring generation** (both in [src/transaction.py](src/transaction.py), used by CLI and web alike):
- `resolve_category(cursor, category_id, description)` — if `category_id` is already given, returns it unchanged; otherwise tries `apply_matching_rule()` against `description`. Called by both `add_transaction()` (CLI) and `POST /api/transactions` (web) whenever the user leaves the category blank — never bypass this by inserting a transaction with a hardcoded category when the user didn't pick one.
- `generate_due_recurring(cursor, as_of=None)` — creates a transaction (via `insert_transaction`, so balances update too) for every active `recurring` row whose `next_due` has arrived, then advances `next_due`. It's idempotent within the same day (nothing left due ⇒ no-op), so it's safe to call on every request. It runs automatically: once at CLI startup (`main_menu`), and on every authenticated request in the web app (`before_request`, after the login check). Don't call it a second time within the same request/command — it's already covered at those two entry points.
- Editing a transaction's category (CLI menu 8 / web `/transactions/<id>/edit`) is the "learn from correction" loop from THIET-KE.md Part 3.5: after `update_transaction_category()`, it logs a `category_overridden` behavior event, then offers to create a `rules` row (`created_from="learned"`) from that transaction's `description` — the user can accept the full description as the pattern or type a shorter keyword instead. Only offered when a real category (not "uncategorized") was picked, since `rules.category_id` is `NOT NULL`.

**Risk metrics** ([src/risk.py](src/risk.py), a separate module from `transaction.py` — analytics is a distinct concern from transaction CRUD): implements THIET-KE.md Part 4 exactly, all four read-only, no writes:
- `short_term_forecast()` (4.1): projected available balance at month-end = liquid balance − recurring still due this month (`get_remaining_recurring_this_month`, only counts `next_due` strictly after today, since anything due today-or-earlier is assumed already turned into a real transaction by `generate_due_recurring`) − projected variable spend (`get_average_daily_variable_spend`, averaged over the trailing 30 days, **excluding `source = 'recurring'` rows** so recurring commitments aren't counted twice) × days left in the month.
- `liquidity_risk()` (4.2) and `runway_months()` (4.3) both build on `get_average_monthly_essential_expense()` — the average essential (`categories.necessity = 'essential'`) spend per calendar month over the last 3 *completed* months (current partial month excluded so it can't skew the average low). Returns `None`/`has_data=False` until there's at least one completed month of essential spending — never silently show a runway/liquidity number computed from zero history.
- `budget_balance_50_30_20(cursor, month)` (4.4): essential/optional spend vs. income for one `'YYYY-MM'` month, grouped via `categories.necessity`.
- `get_reliable_monthly_income()` / `income_sustainability_margin()` (THIET-KE.md 3.7, built alongside the `income_sources` table, not part of the original Part 4 quartet): weights each active income source's `expected_amount` by its `reliability`, then compares that "chắc chắn" (certain) total against `get_average_monthly_essential_expense()` — a different question from `runway_months()`, which only asks how long *existing savings* last with zero income; this asks whether *ongoing* reliable income already covers the essential baseline. `has_data` is `False` until both at least one income source and one completed month of essential spending exist.
- `get_budget_status(cursor, month)` (not in THIET-KE.md, see the `budgets` table above): for every category with an active budget, sums actual `'out'` spend in that category for the given month and compares to `monthly_limit`. Returns an empty list — not an error — when no budgets are set.
- All accept an `as_of` override (defaults to `date.today()`) specifically so they're deterministic to test.
- Exposed via CLI menu option 9 (`show_risk_report`) and the web's `/risk` page — both call the exact same `risk.py` functions and just format the same numbers differently; don't duplicate the math in either UI layer.

**Proactive alerts** ([src/alerts.py](src/alerts.py)): turns `risk.py`'s numbers into user-facing warnings, the "Phòng ngừa" (Guarding) pillar from THIET-KE.md Part 1.3 — surfaced the moment the app opens instead of requiring the user to go check `/risk` themselves. `get_active_alerts(cursor, as_of=None)` is read-only and returns `{"code", "level" ("danger"/"warning"), "message"}` for whichever of short-term-forecast/liquidity/runway/income-sustainability conditions are currently bad; `log_shown_alerts(cursor, alerts)` is a separate call that actually writes `alert_shown` behavior events (THIET-KE.md Part 5's Loss-Aversion/Nudge tracking — this is only the *second* real writer to `behavior_events`, after `category_overridden`). Both are called together: once at CLI startup in `main_menu()` (via a **local** `import alerts` inside the function — `alerts.py` imports `log_behavior_event` from `transaction.py`, so importing `alerts` at `transaction.py`'s module top-level would be a circular import; the lazy import inside the function avoids that because by the time `main_menu()` actually runs, `transaction.py` has already finished loading), and on every load of the web's `/` page (banner shown above the add-transaction form, styled via `.alert-banner.danger`/`.warning` in `PAGE_TEMPLATE`). Not shown on every other page — the "moment the app opens" is specifically the home page, showing it everywhere would just be repeated noise and repeated `alert_shown` events for the same visit.

**Screenshot import via Gemini** ([src/ocr_import.py](src/ocr_import.py), web-only — see below for why): the user's workflow is to add a clear note to every MoMo/MB Bank transfer, then upload screenshots. **This used to be local Tesseract OCR + regex line-parsing** (see git history around 2026-07-24) — that approach was replaced after Tesseract kept misreading real screenshots in ways plain regex couldn't recover from: garbled/dropped labels, and a two-column layout sometimes read as "all labels, then all values" instead of label-value pairs in order, each needing a new, increasingly fragile heuristic (`_find_labeled_note`, `_find_note_before_footer`, `_find_ascii_lowercase_note`, `_clean_mb_noi_dung`, `_find_mb_content_value`, junk-character filters, ... — all deleted when this was replaced). A vision model reads the screen semantically instead of line-by-line, so it isn't tripped up by OCR reading order.
- **This is a real, deliberate trade-off, not a free upgrade**: the original Tesseract choice was made specifically so screenshots of real financial data never left the user's machine. Switching to Gemini means those photos are now sent to Google's API. The user made this trade-off explicitly after Tesseract's accuracy problems proved hard to fix with more regex patches (see memory `project_stage2_progress`) — don't revert it back to local-only OCR without the user raising it again, and don't casually add *other* cloud calls elsewhere in the app on the assumption this precedent makes it fine.
- `analyze_image(image_bytes, mime_type)` sends the image straight to the Gemini API (`google.genai`, model configurable via `GEMINI_MODEL` env var, defaults to `gemini-flash-latest`) with a prompt asking it to return structured JSON (`response_mime_type="application/json"`, `response_schema=` a Pydantic model) — one `{amount, direction, note}` object per real transaction found in the image. This replaces the *entire* old regex pipeline in one call; there is no separate "raw OCR text" step anymore, and no per-screen-shape special-casing to maintain — the prompt itself explains what a "note" is vs. a bank reference code, and asks the model to skip balance-only lines and to not double-count a restated amount.
  - `gemini-flash-latest` (an alias, not a dated model name) was picked deliberately over pinning e.g. `gemini-2.5-flash` — that pinned name actually failed at runtime with a real key ("no longer available to new users"), confirming Gemini model names churn fast enough that hardcoding a specific version is a real reliability risk. Confirmed working end-to-end (correct amount/direction/note) against several test images with a real API key on 2026-07-24. If this alias ever breaks, check `client.models.list()` for what's currently available rather than guessing a name from memory.
- Requires `GEMINI_API_KEY` in the environment — checked lazily (only when `analyze_image` is actually called), so the rest of the app works fine without it; only the `/import` page needs it. Get a free key at [aistudio.google.com/apikey](https://aistudio.google.com/apikey).
- A light `(amount, direction)` dedupe still runs in Python after Gemini's response, as a defensive belt-and-suspenders check — the prompt already asks the model not to double-count, but this catches it if the model doesn't perfectly comply.
- `make_external_ref(amount, direction, note)` — since there's no bank reference number to key off, the dedupe key is a hash of `(amount, direction, note)`. Re-uploading the same screenshot produces the same hash, which collides with `transactions.external_ref`'s UNIQUE constraint; `web_app.py`'s `/import/confirm` catches `sqlite3.IntegrityError` per-row (committing after each successful insert, so one duplicate doesn't roll back the others in the same batch) and just skips that row. Unchanged from the Tesseract-era design.
- **Category is also AI-suggested, not just amount/direction/note**: `analyze_image` is given the full category tree (via `_format_categories`, built from `category_tree_as_json` for both kinds) as part of the prompt, and asked to return a `category_id` guessed from the *meaning* of the note (e.g. "tien gui xe" → a parking/transport category) — broader than `rules`' exact-substring matching. `analyze_image` validates any returned id against the real category set before trusting it (never take a model-generated foreign key on faith, even for a low-stakes field). In `web_app.py`'s `import_page()`, Gemini's guess wins; the existing `apply_matching_rule` (Stage 2's rules engine) is only consulted as a fallback when Gemini returns `null` (not confident enough to guess). Confirmed with a real API key across several notes — correctly distinguished categories like "Cà phê/Trà sữa" vs. "Ăn ngoài" vs. "Gửi xe" from note wording alone, and fell back sensibly (e.g. "Thu nhập khác") when no category was an exact fit.
- **Review happens before insert, not after**: `/import` (upload) → `analyze_image` per file → pre-fills a form per candidate (amount, direction, note, and now category) → user edits/deselects anything wrong → `/import/confirm` is what actually calls `insert_transaction(..., source="ocr", is_reviewed=0)`. Nothing extracted is ever written to the database without a human seeing it first — this safety property held under Tesseract and still holds under Gemini; don't remove it just because Gemini is more accurate.
- This feature is **web-only, no CLI equivalent** — unlike everything else in this app, "upload a phone screenshot" only makes sense from a phone browser. Don't try to add a CLI menu option for it.

**Balance maintenance**: all writes go through `insert_transaction()` in `transaction.py`, which inserts the row and adjusts `accounts.current_balance` in the same call — there's no trigger. Any new code path that inserts into `transactions` must call this function rather than writing its own INSERT.

**Shared core vs. CLI vs. web** ([src/transaction.py](src/transaction.py)): the file has two halves, marked by `# ----` section comments. The data-layer half (`get_active_accounts`, `get_categories`, `insert_transaction`, `get_recent_transactions`, `get_transaction_by_id`, `update_transaction_category`, `log_behavior_event`, `get_monthly_totals`, `get_income_sources`, `add_income_source`, `get_budgets`, `set_budget`, `get_event_templates`, `get_event_template_items`, `create_event_plan`, `add_event_plan_item`, `get_event_plans`, `get_event_plan_items`, plus the rules/recurring functions listed above) has no `input()`/`print()` and is imported by both the terminal CLI further down in the same file and by `web_app.py`. The CLI half (`display_accounts`, `add_transaction`, `list_transactions`, `edit_transaction_category_interactive`, `monthly_summary`, `show_risk_report`, `add_rule_interactive`, `list_rules_interactive`, `add_recurring_interactive`, `list_recurring_interactive`, `add_income_source_interactive`, `list_income_sources_interactive`, `set_budget_interactive`, `show_budget_status_interactive`, `list_event_templates_interactive`, `create_event_plan_interactive`, `list_event_plans_interactive`, `main_menu`) is the terminal UI (menu options 1–16), built on top of that data layer. **When changing how a transaction, rule, or recurring item is read or written, change the shared function once** — don't patch `web_app.py`'s SQL and `transaction.py`'s SQL separately, they're meant to stay identical by construction, not by manual sync.

**Web form** ([src/web_app.py](src/web_app.py)): a Flask alternative to the CLI, for using the tracker from a phone browser instead of the terminal. Routes mirror the CLI's transaction-related menu options: `/` (add transaction — the only one that's a JS single-page form posting to `POST /api/transactions` via `fetch()`, so it never reloads), `/transactions` (recent list, each row links to `/transactions/<id>/edit` for changing its category — a normal POST-and-redirect form, not AJAX), `/summary` (monthly totals, month picked via a native `<input type="month">` that auto-submits on change), `/risk` (the risk metrics from Part 4 plus income sustainability and the "Hũ chi tiêu" budget-status bars, read-only), `/import` + `/import/confirm` (OCR screenshot import — the CLI has no equivalent, see above). Rule, recurring, income-source, and event-plan *management* (creating/listing them — CLI menu 4–7, 10–16) has no web equivalent — extend the web app only if asked; the data they produce already shows up on these pages regardless of which interface created it, since both read the same tables. All pages share one inline CSS block (`BASE_STYLE`, plain string — deliberately not an f-string, so CSS `{ }` don't need escaping) and a nav bar linking between all five main pages. HTML/CSS/JS is inlined via `render_template_string` — no `templates/` folder.

**Auth on the web form**: single shared password, not per-user login (deliberate — see memory `project_web_form_multiuser_phase`: the goal right now is letting many people log transactions with minimal friction, not tracking who entered what). `APP_PASSWORD` is read from the environment and never hardcoded — the app refuses to start without it. A Flask session cookie (`session["authenticated"]`), valid 30 days, gates every route via a `before_request` hook except `/login`; `/api/*` returns 401 JSON instead of a redirect when unauthenticated. `SECRET_KEY` may also be set via env; if omitted it's a random value generated per-process, meaning all sessions invalidate on every restart — acceptable for this use case, don't "fix" it without being asked.

## Code conventions actually in use

- Function/variable/constant names and comments across `transaction.py`, `seed_data.py`, `init_db.py` are in **English**, per docs/THIET-KE.md Part 6. User-facing text passed to `print()`/`input()` stays in **Vietnamese** — that's the target audience's language, not a convention to migrate away from.
- Money is always stored as integer VND (no decimals).
- Timestamps are stored as `TEXT` via `datetime.now().strftime("%Y-%m-%d %H:%M:%S")` / SQLite `datetime('now')`.
