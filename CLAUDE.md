# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A personal finance tracker ("Quản lý tài chính cá nhân") built as Python + SQLite, usable from either a terminal CLI or a Flask web form. The project follows the 7-stage roadmap in [docs/THIET-KE.md](docs/THIET-KE.md) (Vietnamese design doc — read it before making schema or product-behavior decisions, it is the authoritative spec). **Stage 1** and **Stage 2** (auto-categorization, recurring transactions, learn-a-rule-from-correction) are fully built. **Stage 6** (Part 4's risk metrics, Part 1.3's proactive alerts, Part 3.7's income sources, and Part 3.8's event planning) and the **Stage 4** screenshot import are also built, all picked up out of roadmap order, deliberately: risk metrics and alerts needed no external data; income sources and event planning were requested directly, inspired by looking at MoMo/Timo's own features (see memory `project_stage2_progress`); screenshot import (`/import` in the web app, [src/ocr_import.py](src/ocr_import.py)) is now powered by the Gemini API's image understanding rather than local OCR, after local Tesseract's accuracy on real screenshots proved hard to fix with regex (see the file's own module docstring and CLAUDE.md's Architecture section for the full story). **Stage 3 (auto-reading MB Bank emails) was skipped, not just deferred** — the user found it's blocked by iOS email-access restrictions, so screenshot import (Stage 4) became the real path for semi-automated import instead. Stage 7 (investments/gold/FX) still has no logic — only a schema-only placeholder table (see below). `budgets` (category-level "Hũ chi tiêu" budgeting) also isn't in THIET-KE.md at all — added by direct request, inspired by Timo, not part of the original design; **now itself superseded by `period_budgets`** (see below), kept around unwritten-to rather than dropped. **The web UI is now a deliberate two-tier mix, not uniformly plain**: `/transactions`, `/summary`, `/rules`, and `/budgets` use Tailwind CSS (via CDN, see below) per a detailed visual brief from the user (generous whitespace, large touch targets, amount as the most visually prominent element, calm/neutral palette, no default-template look); `/`, `/risk`, `/import`, and the edit-transaction page are still the original plain inline-CSS design (`BASE_STYLE`) and were explicitly left alone in that same request, one step at a time, not because they were forgotten.

**2026-07-26: a second, much larger expansion beyond the original 7-stage roadmap began** — moving the app from "ghi nhận quá khứ" (recording the past) to "hoạch định tương lai" (planning the future), the user's own framing. Requested as 5 sequential milestones under one approved plan, executed one after another with a short report at the end of each (not waiting for per-milestone approval): **Mốc 1 (period-based budgeting + AI infrastructure), Mốc 2 (financial goals), Mốc 3 (spending-decision simulation), and Mốc 4 (cashflow forecasting) are done** — see the dedicated sections below (`period.py`, `services/ai_client.py`, migrations, `/budgets`, `goals`, `/goals`, `/events`, `spending_simulations`, `/simulate`, `cashflow_forecasts`, `/forecast`). **Mốc 5 (health-score dashboard replacing `/`) is not yet built** — don't assume any of its schema/routes exist until its own milestone's CLAUDE.md section appears here. The single biggest structural change Mốc 1 made: **every period-shaped calculation in the app now uses a configurable financial period (default the 15th of one month through the 14th of the next) instead of the calendar month** — see `period.py` below; this was a deliberate retrofit of already-shipped `risk.py` code, not just new code, because the user was explicit that "every period-based calculation must use this cycle, not the calendar month."

`init_db.py`, `seed_data.py`, `transaction.py`, `risk.py`, and `period.py` use only the Python standard library. `web_app.py` needs Flask, `ocr_import.py` and `services/ai_client.py` need `google-genai` + `pydantic`, and all of them together need `python-dotenv` (all four in `requirements.txt`) plus a `GEMINI_API_KEY` (get one free at [aistudio.google.com/apikey](https://aistudio.google.com/apikey)) for anything AI-powered — see Commands below.

## Commands

```bash
# One-time: install third-party Python dependencies (Flask, google-genai, pydantic, python-dotenv)
pip3 install -r requirements.txt

# One-time: copy the env template and fill in real values (never commit .env — already gitignored)
cp .env.example .env

# Create the database and tables from schema.sql (data/finance.db, gitignored)
# Also creates the data/ directory itself if it doesn't exist yet (needed on a fresh clone —
# data/ has no tracked file inside it, since *.db is gitignored, so git never brings the folder along).
python3 src/init_db.py

# Apply any pending migrations from src/migrations/*.sql (additive schema changes since
# schema.sql was written — see "Migrations" below). Safe to re-run: tracks what's already applied.
python3 src/migrate.py

# Seed initial accounts and categories (safe to re-run: no-ops if categories already exist)
python3 src/seed_data.py

# Run the once-only unittest suite (period.py's date math + risk.py's retrofitted period metrics)
python3 -m unittest discover -s tests

# Run the interactive terminal CLI (add transaction / list recent / monthly totals)
python3 src/transaction.py

# Run the web form instead (same feature as "add transaction" in the CLI, browser-based)
# APP_PASSWORD is required — the app raises RuntimeError at import time if it's unset.
# GEMINI_API_KEY is only needed for /import (OCR) and every /api/ai/* route — everything else
# works without it. Both (plus SECRET_KEY, GEMINI_MODEL, GEMINI_MODEL_HEAVY) can live in .env
# instead of being exported by hand every time — web_app.py calls load_dotenv() before reading any of them.
APP_PASSWORD=your_shared_password GEMINI_API_KEY=your_key python3 src/web_app.py
# Serves on http://0.0.0.0:8000 — reachable from other devices (e.g. a phone) on the same LAN.
# Port 8000, not 5000: macOS AirPlay Receiver squats on 5000 by default.
```

To reset the database from scratch: delete `data/finance.db`, then re-run `init_db.py`, `migrate.py`, and `seed_data.py` in that order. **After pulling a change to `schema.sql`, re-run `python3 src/init_db.py` against your existing `data/finance.db`** — every statement in it is `CREATE TABLE IF NOT EXISTS`, so this only adds newly-introduced tables and never touches or drops existing data. **After pulling a new file under `src/migrations/`, re-run `python3 src/migrate.py`** the same way — see "Migrations" below for why this is a separate step from `init_db.py`.

## Architecture

**Storage**: single SQLite file at `data/finance.db`, gitignored (per docs/THIET-KE.md, real financial data must never be committed). Every module resolves the project root as `Path(__file__).parent.parent` and connects with `PRAGMA foreign_keys = ON` and `row_factory = sqlite3.Row`.

**Schema** ([src/schema.sql](src/schema.sql)), defined and explained in full in docs/THIET-KE.md Part 3:
- `accounts` — one row per money store (bank, ewallet, credit_card, cash, savings). `is_liquid` flags whether it counts toward liquidity/emergency-fund calculations (e.g. credit card debt is not liquid).
- `categories` — self-referencing tree via `parent_id`. `kind` is expense/income/transfer. `necessity` (essential/optional) powers the risk metrics in `risk.py` (50/30/20 rule, "months of runway" if income stops — see below). `stability` (fixed/variable) is still unread by any code — don't drop it anyway, it's designed-in for later.
- `transactions` — the central table. `amount` is always positive; sign is carried separately in `direction` (in/out). `source` is `manual`/`recurring`/`ocr` in practice today (`email` is in the schema's CHECK constraint but has no writer — Stage 3 was skipped, see overview). `is_reviewed` exists for a not-yet-built *batch* review workflow; both `recurring`- and `ocr`-sourced transactions are inserted with `is_reviewed = 0` (manual entries are `1`) even though OCR imports already go through a review-and-edit screen at import time — that inline review is a per-batch safety step, not the same thing as the design doc's dedicated "chờ duyệt" screen, which still doesn't exist. `external_ref` is the dedupe key; OCR import is its first real user (see below).
- `behavior_events` — structure existed unwritten-to since Stage 1 by deliberate design (see THIET-KE.md Part 5: "tạo cấu trúc từ Giai đoạn 1, chỉ ghi dữ liệu thật từ Giai đoạn 2"). Now has two real writers: `category_overridden` (`log_behavior_event`, used when a transaction's category is edited) and `alert_shown` (`alerts.log_shown_alerts`, used when a risk warning is displayed — see below). Other event types (`transaction_reviewed`, `alert_acted_on`, etc.) still have no writer — don't add one before the feature that produces that event actually exists.
- `rules` — auto-categorization: `pattern` is matched case-insensitively as a substring of a transaction's `description`; on match, `category_id` is assigned and `hit_count` increments. Tried highest-`priority` first. `created_from` distinguishes rules added directly (`'user'`, via CLI menu option 4) from ones learned by correcting a transaction's category (`'learned'`, via CLI menu option 8 or the web's edit-transaction page).
- `recurring` — recurring transaction templates (rent, subscriptions, ...). `next_due` advances by `frequency` (monthly/quarterly/yearly) each time it fires; `day_of_period` is stored but not currently used to compute due dates (next_due is set explicitly and advanced from itself, not recalculated from day_of_period — don't assume it's authoritative). Added via CLI menu option 6 only.
- `income_sources` — THIET-KE.md 3.7: each row is one income stream (a teaching job, a scholarship, freelance work, ...) with an `expected_amount` and a `reliability` (0–100%). The point of keeping this separate from `transactions` income history is right there in the design doc: a side gig's *expected* amount shouldn't be treated as certain just because it's expected — `reliability` is what lets `risk.py` discount it. Added via CLI menu option 10 only.
- `budgets` — **not in THIET-KE.md**, added by request inspired by Timo's "Hũ chi tiêu" (envelope budgeting per-category — THIET-KE.md 7.3 itself notes this general method as "chưa triển khai" at design time). One row per category with an active `monthly_limit`; `set_budget()` upserts (one active budget per category — setting it again replaces the limit, it doesn't insert a confusing duplicate row).
- `event_templates` / `event_items` (THIET-KE.md 3.8): a template (Chuyển nhà, Cưới hỏi, Du lịch — seeded in `seed_data.py`'s `_seed_event_templates`, guarded by its own count check so it seeds independently even on a re-run where categories already exist) with suggested line items. **Item *names* only, never a suggested price** — that's the design doc's explicit principle (price depends on locale/circumstances, guessing it would be wrong and erode trust), strictly followed when picking Cưới hỏi/Du lịch's item lists too (well-known checklist items, not financial advice).
- `event_plans` / `event_plan_items` — a real plan the user builds, optionally from a template (`template_id` nullable — a plan can be fully custom). `event_plan_items` is **not explicitly named in THIET-KE.md** but is a necessary, directly-justified extension of it: the doc says `event_plans` should carry "expected vs. actual" amounts, and that only makes sense tracked per line item. `expected_amount` is user-entered per item when creating the plan (CLI menu 15, `create_event_plan_interactive`); `actual_amount` exists in the schema for the same reason but **has no CLI/web writer yet** — don't assume it's populated anywhere.
- Tables described in the design doc but still **not in schema.sql**: `income_sources`' sibling concept from Part 7 (theory background, not a table) and anything from later stages (email/OCR-adjacent). When implementing a later stage, add tables incrementally rather than scaffolding them all up front.

**Migrations** ([src/migrations/](src/migrations/) + [src/migrate.py](src/migrate.py), added 2026-07-26 for the "hoạch định tương lai" expansion): `schema.sql`'s `CREATE TABLE IF NOT EXISTS` pattern stays as the original, once-only schema and is **never edited retroactively** — every table added since is a numbered file (`001_ai_infra.sql`, `002_period_settings.sql`, `003_period_budgets.sql`, `004_goals.sql`, `005_simulations.sql`, `006_cashflow_forecast.sql`, ...), each purely additive (`CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ... ADD COLUMN`, never `DROP`). `migrate.py` tracks which filenames have already run in a `schema_migrations` table, which exists specifically because SQLite has no `ADD COLUMN IF NOT EXISTS` — re-running the same `ALTER TABLE` twice raises `duplicate column name`, so unlike `schema.sql`, a migration file is *not* naturally safe to execute more than once on its own; the tracking table is what makes `migrate.py` itself safe to re-run. Current tables added this way (none are in `schema.sql`, none in docs/THIET-KE.md's original Part 3):
  - `ai_cache` / `ai_calls` (`001_ai_infra.sql`) — see `services/ai_client.py` below.
  - `app_settings` (`002_period_settings.sql`) — generic key-value config; today holds exactly one key, `period_start_day` (default `'15'`), read/written through `period.py`, never queried directly elsewhere. A settings table rather than an env var specifically because the user wants to reconfigure the period's start day at runtime, which an env var can't do without a restart.
  - `period_budgets` (`003_period_budgets.sql`) — supersedes `budgets`/`get_budget_status` (still in `schema.sql`/`risk.py`, deliberately untouched — see below) for anything period-aware. One row per `(category_id, period_id)` — `period_id` is a `period.py` id (see below), not a calendar month — with an `amount` and a `source` (`manual` / `suggested_fixed` / `suggested_variable` / `ai_adjusted`) recording *how* that number got there.
  - `goals` (`004_goals.sql`, Mốc 2) — see "Financial goals" below. Same migration also `ALTER TABLE event_plans ADD COLUMN`s three new columns onto the pre-existing `event_plans` table (`event_date`, `linked_goal_id`, `goal_prompt_dismissed`) — `event_plans` had **no date field at all** until this migration; found missing while designing the goals↔event-plan link and added because the link structurally needs it, not speculative scaffolding.
  - `spending_simulations` / `spending_simulation_scenarios` (`005_simulations.sql`, Mốc 3) — see "Spending-decision simulation" below. `spending_simulations.baseline_balances` and `.ai_recommendation` are both **frozen at creation/first-AI-call time**, never recomputed on a later page view — the whole point of saving a simulation is to look back later and see what was actually projected/recommended *then*, not a number that's silently drifted since.
  - `cashflow_forecasts` / `cashflow_forecast_periods` (`006_cashflow_forecast.sql`, Mốc 4) — see "Cashflow forecasting" below. `scenario` distinguishes `'base'` from `'macro_adjusted'`; a macro-adjusted row's `base_forecast_id` points back at the base it was derived from, and its own `macro_adjustment`/`macro_context_note`/`macro_context_sources` are a durable copy of what was actually shown/applied at the time — same "freeze it, don't recompute later" reasoning as the simulation tables above.
  - `investment_assets` (planned, Stage 7 prep) — schema-only placeholder once added, no reader/writer code; **don't build Stage 7 logic just because the table exists**.

**Financial periods** ([src/period.py](src/period.py), added 2026-07-26): a "kỳ" (period) is a configurable cycle — default the 15th of one month through the 14th of the next (`app_settings.period_start_day`) — that replaced the calendar month for every period-shaped calculation in the app, per the user's explicit instruction that this must apply everywhere, not just new features. Pure date-math functions (`period_bounds(d, start_day)`, `period_id_for`, `period_bounds_for_id`, `shift_period_id`, `recent_period_ids_for`, `days_elapsed_and_remaining_for`) take `start_day` directly and have no DB dependency, specifically so they're unit-testable without a cursor (see `tests/test_period.py` — 18 cases, the **first test suite in this project**, covering boundary dates, year rollover, and start-day clamping in short months); each has a cursor-based convenience wrapper (`get_period_start_day`, `current_period_id`, `recent_period_ids`, `days_elapsed_and_remaining`) that reads the configured start day and delegates. A `period_id` is formatted like a calendar month (`"YYYY-MM"`, the period's start date) so it sorts the same way old month strings did, **but it is not a calendar month** once `period_start_day != 1` — don't compare a `period_id` against `strftime('%Y-%m', ...)` output as if they were interchangeable. `period.py` deliberately has zero dependency on `transaction.py`/`risk.py` (it's a leaf both of those import) — its own tiny `_add_months` duplicates `transaction.py`'s day-clamping helper on purpose rather than importing it, to avoid a circular import.

**Financial goals** ([src/transaction.py](src/transaction.py)'s `goals` CRUD + [src/risk.py](src/risk.py)'s `get_goal_progress`/`suggest_emergency_fund_target`, added 2026-07-26 as Mốc 2): a `goal` (`get_goals`/`get_goal_by_id`) is a long-running accumulation target — name, `goal_type` (`emergency_fund`/`savings`/`investment`/`medical`/`custom`, labeled via `web_app.py`'s `GOAL_TYPE_LABELS`), `target_amount`, `deadline`, and a required `account_id`. **Progress is read live from that account's `current_balance`, not a separately-tracked running total** — a deliberate simplicity trade-off: if two goals point at the same account, each independently shows that account's full balance (no automatic splitting of one pool across goals). This was weighed against adding a `current_amount` column that `insert_transaction`/`delete_transaction` would need to keep in sync, and rejected specifically to avoid a second source of truth that could drift from the account's real balance.
- `risk.get_goal_progress(cursor, goal, as_of=None)`: `progress_pct` (capped at 100), `remaining_amount`, `periods_remaining` and `required_per_period` (both via `period.periods_between`, inclusive of the current and deadline periods), and an `is_off_track` flag — **a simple LINEAR schedule comparison** (expected % = periods elapsed since the goal's `created_at` ÷ total periods to deadline), explicitly **not** a real forecast; Mốc 4's cashflow forecast is the intended home for anything more sophisticated than "are you roughly on a straight-line pace." `is_overdue` (deadline passed, target not yet met) takes precedence over `is_off_track` so a goal is never flagged both ways at once.
- `risk.suggest_emergency_fund_target(cursor)`: the `emergency_fund` goal type's own built-in suggestion — 6× `get_average_period_essential_expense()`, the upper end of THIET-KE.md 7.3's "quỹ khẩn cấp 3–6 tháng" band (same source `runway_months`' reference bands already use). Returns `None` under the same has-data convention as the function it wraps; `/goals/new`'s JS only auto-fills the target field from this suggestion when the user hasn't already typed one.
- **`event_plans` ↔ `goals` linkage, per the user's own proposed division of labor**: `event_plans` = a specific, usually 1–2-period event (a trip, a birthday); `goals` = a multi-period accumulation target. `web_app.py`'s `events_new()` fires a **one-time** prompt — never a recurring nag — right after creating an event plan, when `SUM(event_plan_items.expected_amount) >= 10,000,000đ` **and** the event is `>= 2` periods away (via `period.periods_between`); the created plan redirects to `/events/<id>?suggest_goal=1`, which shows the prompt only if `linked_goal_id` is still null **and** `goal_prompt_dismissed` is still 0. Accepting pre-fills `/goals/new` via query params (name/target/deadline from the event); declining calls `dismiss_event_plan_goal_prompt()`, which sets the flag permanently — the prompt never resurfaces for that plan either way once acted on.
- **`/events` + `/events/new` is a new web equivalent for what was previously CLI-only** (menu 14–16) — added specifically so the event↔goal linkage above is reachable at all from the phone browser, the app's primary surface; without it, creating an `event_plan` (the trigger for the whole feature) would have stayed impossible from the web. `events_new()`'s form supports picking one of the seeded `event_templates` (pre-fills its `event_items` as read-only name fields with a blank amount input each, exactly like the CLI's own "chỉ gợi ý khoản mục, giá tự nhập" flow) plus a handful of blank custom-item rows, submitted together in one POST.
- Multi-goal AI prioritization (`/api/ai/goal-priority`, only surfaced on `/goals` when `len(goals) >= 2`) sends each goal's already-computed `remaining_amount`/`periods_remaining`/`required_per_period` and asks the AI to rank them and explain why, citing common personal-finance heuristics (emergency fund before investment, high-interest debt before savings) only where relevant — never computing new numbers itself, same standing rule as every other `ai_client` call.

**Spending-decision simulation** ([src/risk.py](src/risk.py)'s `compute_spending_scenarios`/`project_simple_trajectory`/`get_baseline_period_flow`/`traffic_light_for_trajectory` + [src/transaction.py](src/transaction.py)'s `spending_simulations` CRUD, added 2026-07-26 as Mốc 3): "before you buy something big, see the impact first."
- `project_simple_trajectory(cursor, periods_ahead, extra_expenses=None)`: projects liquid balance forward by continuing the recent average income/expense flat (`get_baseline_period_flow`, itself just reusing `get_savings_rate_trend`'s own data rather than re-querying). **Deliberately simple, not a real forecast** — no seasonality, no goals, no budgets layered in. This exists purely to power Mốc 3's "with vs. without this expense" chart; **Mốc 4's cashflow forecast is a separate, richer model and should not just extend this function in place** — check whether Mốc 4's own forecast already supersedes this before touching it.
- `compute_spending_scenarios(cursor, *, item_amount, maintenance_cost_per_period=0, expected_lifetime_periods=0)`: builds all 6 comparison scenarios in one call — pay now, installments over `INSTALLMENT_OPTIONS` (3/6/12 periods), delay by `DELAY_OPTIONS` (3/6 periods) — plus the no-expense baseline. `total_cost_of_ownership` (`item_amount + maintenance × lifetime`) is **identical across every scenario** — no financing/interest cost is modeled, since none was asked for and an invented interest rate would be a number this app has no basis to assume; only the *timing* of the cash outflow differs between scenarios. Every number here is plain Python arithmetic — no AI involved anywhere in this function.
- `traffic_light_for_trajectory`: green/yellow/red, reusing the *same* essential-period-expense threshold `liquidity_risk` already uses for "sufficient" (not a new, separately-invented threshold) — red if any projected period goes negative, yellow if it dips below that threshold without going negative, green otherwise; falls back to a plain negative/non-negative check (no yellow tier) when there's no essential-spend history yet to know the threshold from.
- **The AI's role is explanation only, and it never sees raw numbers it could second-guess into a new one** — `/api/ai/simulation-advice` sends each scenario's already-computed `total_cost_of_ownership`/`traffic_light`/`projected_balances` and asks for 1 sentence of pros + 1 of cons per scenario, plus one clear recommendation with reasoning — never asked to compute anything. Runs on `GEMINI_MODEL_HEAVY` (not the default flash-tier model) per the user's own request that Mốc 3/4 use the heavier model for analysis — **this is the first real usage of `GEMINI_MODEL_HEAVY`/`gemini-pro-latest`, unconfirmed against a real key as of this writing** (see `services/ai_client.py`'s own note about needing a live smoke test).
- **The recommendation freezes permanently on first success**: `/api/ai/simulation-advice` checks `spending_simulations.ai_recommendation` first — if already set, returns it directly with no API call at all; only calls `get_ai_suggestion` (and then writes the result back via `set_simulation_ai_recommendation`) the first time. This is stronger than `ai_client`'s own TTL-based cache (which would still exist underneath, keyed on `task="simulation_advice"`, but is effectively moot here since the frozen column is always checked first) — deliberately so, because the whole point of saving a simulation is to compare a past recommendation against what actually happened later, which a refreshable cache would undermine.
- **Triggered contextually from `/` (Mốc 3's own requirement)**: `PAGE_TEMPLATE`'s existing add-transaction JS now intercepts `POST /api/transactions` submissions where `direction === "out"` and `amount >= 1,000,000` with a native `confirm()` ("bạn có muốn mô phỏng trước khi lưu không?"); accepting navigates to `/simulate?amount=...&name=...` **without saving the transaction** — the user simulates first, then (if they still want to) goes back and logs the real transaction separately. This is a functional addition to `/`'s existing JS, not a visual redesign, so it doesn't conflict with `/` otherwise staying on the old `BASE_STYLE` system.
- **First use of a JS charting library in this project** (`SIMULATION_DETAIL_TEMPLATE` only, not global): Chart.js loaded from `https://cdn.jsdelivr.net/npm/chart.js@4`, **pinned to a major version** unlike Tailwind's floating CDN tag — Chart.js's API has real breaking changes across major versions, and this project already has a concrete lesson (`gemini-2.5-flash`'s alias-vs-pinned-name incident) about what an unpinned identifier changing underneath the app looks like. The chart itself shows exactly 2 lines (baseline vs. pay-now-with-the-expense), not all 6 scenarios overlaid — the rich multi-scenario comparison lives in the table below it instead, matching the spec's own "số liệu trước, khuyến nghị sau" (numbers first, then verdict) ordering and keeping the chart itself readable.

**Cashflow forecasting** ([src/risk.py](src/risk.py)'s `compute_cashflow_forecast`/`project_recurring_by_period`/`detect_seasonality` + [src/transaction.py](src/transaction.py)'s `cashflow_forecasts` CRUD, added 2026-07-26 as Mốc 4): projects liquid balance 6–12 periods ahead, chaining each period's ending balance into the next one's start (the "rollover" the user asked for — `accounts.current_balance` itself never needed any new rollover logic, since it's already a continuously-running total; this chaining is purely internal to the forecast loop).
- **Inputs, combined without double-counting**: `project_recurring_by_period(cursor, period_ids)` simulates each active `recurring` item's *own* occurrences forward from its real `next_due`/`frequency` (a quarterly item does not appear in every period — verified in `tests/test_risk.py`), giving real per-period recurring in/out. `get_reliable_monthly_income()` (already built for Mốc 2's `income_sustainability_margin`) is applied every period as the "chắc chắn" income floor. The user's own manual per-period estimates for uncertain income (`irregular_income_by_offset`, a `{period_offset: amount}` dict) cover THIET-KE.md 3.7's "thu nhập thất thường" case. **"Ngân sách đã lập" (`period_budgets`) is deliberately NOT folded into the forecast number itself** — a budgeted category can also be a recurring item, and reconciling that overlap correctly (without either double-counting or silently dropping spend) was judged too real a correctness risk for the time available; instead "other variable spend" uses the same historical-average approach as Mốc 3's `project_simple_trajectory` (recent average total expense minus recent average recurring expense). If a future pass wants budgets to feed the number directly, that reconciliation still needs solving, not just wiring the columns together.
- **Goals feed in as a genuinely new outflow, not a double-count**: the caller (web_app.py's `_total_goal_contribution_per_period`) sums every non-overdue active goal's `required_per_period` (from `get_goal_progress`, Mốc 2) and passes the total in as `goal_contribution_per_period` — applied as a flat amount every period in the forecast window. **Known simplification, documented not silently assumed**: a goal's contribution keeps applying even past that goal's own deadline within the forecast window, since properly stopping it at the right offset would need per-goal period-by-period bookkeeping this function doesn't do.
- **Seasonality detection is descriptive statistics only, and never applies itself**: `detect_seasonality(cursor)` computes mean/stdev total 'out' spend per calendar-month-position across every *completed* period of history, comparing each month's average against the overall average; a month only becomes a "pattern" if it's been observed ≥2 times and differs from the overall average by ≥`SEASONALITY_PCT_THRESHOLD` (15%), and only runs at all once ≥`SEASONALITY_MIN_PERIODS` (12) periods of history exist (need at least one full annual cycle to say anything). Both thresholds are fixed Python constants — **the AI is never involved in detection or in deciding the threshold**, only (nowhere yet built, but reserved as a future touchpoint) in describing a detected pattern in plain language, per the user's explicit "AI diễn giải căn cứ đó, nhưng ngưỡng tin cậy do công thức quyết định." A detected pattern only ever affects a forecast when the user explicitly ticks "Áp dụng quy luật mùa vụ" on `/forecast`'s generate form — `compute_cashflow_forecast`'s `seasonality_patterns` parameter is the only way it reaches the calculation, and nothing populates it automatically.
- **The macro-context layer is real but genuinely separate and low-confidence**: `services/ai_client.py`'s `get_macro_context(cursor, prompt)` is a **dedicated function, not `get_ai_suggestion`** — Gemini's Google Search grounding tool (`types.Tool(google_search=types.GoogleSearch())`) doesn't reliably combine with forced structured JSON output, so this call requests plain text and parses `response.candidates[0].grounding_metadata.grounding_chunks[].web.{title,uri}` for sources — **this exact parsing shape is UNCONFIRMED against a real API response as of this writing**, flagged the same way the OCR model-alias lesson is elsewhere in this doc; verify live before trusting it, don't assume it just works. Gated off by default (`ENABLE_MACRO_CONTEXT` env var, unset/anything-but-`"1"` = disabled) and, even when enabled, only ever fetched by an explicit button click on `/forecast` (`/api/ai/macro-context`), never auto-loaded — the single most expensive/slowest/least deterministic AI feature in the app, deliberately shipped last and opt-in only, per the plan's own risk callout. Its output is shown in a visually separate card, explicitly labeled as general market information, not personal financial advice, and **never mixes into the forecast numbers automatically**: applying it requires the user to type their own adjustment amount (a real number they choose, informed by but not computed by the AI) into a small form, which creates a brand-new `scenario='macro_adjusted'` forecast (`/forecast/<id>/macro-scenario`) sitting *alongside* the original base forecast (linked via `base_forecast_id`), never overwriting it.
- Exposed via `/forecast` (shows the latest base forecast + the generate-new form + seasonality suggestion box + the gated macro-context section) and `/forecast/<id>` (any specific forecast, base or macro-adjusted, by id — also how a macro-adjusted scenario and its base are cross-linked for side-by-side comparison).

**Auto-categorization and recurring generation** (both in [src/transaction.py](src/transaction.py), used by CLI and web alike):
- `resolve_category(cursor, category_id, description)` — if `category_id` is already given, returns it unchanged; otherwise tries `apply_matching_rule()` against `description`. Called by both `add_transaction()` (CLI) and `POST /api/transactions` (web) whenever the user leaves the category blank — never bypass this by inserting a transaction with a hardcoded category when the user didn't pick one.
- `generate_due_recurring(cursor, as_of=None)` — creates a transaction (via `insert_transaction`, so balances update too) for every active `recurring` row whose `next_due` has arrived, then advances `next_due`. It's idempotent within the same day (nothing left due ⇒ no-op), so it's safe to call on every request. It runs automatically: once at CLI startup (`main_menu`), and on every authenticated request in the web app (`before_request`, after the login check). Don't call it a second time within the same request/command — it's already covered at those two entry points.
- Editing a transaction's category (CLI menu 8 / web `/transactions/<id>/edit`) is the "learn from correction" loop from THIET-KE.md Part 3.5: after `update_transaction_category()`, it logs a `category_overridden` behavior event, then offers to create a `rules` row (`created_from="learned"`) from that transaction's `description` — the user can accept the full description as the pattern or type a shorter keyword instead. **Risk metrics** ([src/risk.py](src/risk.py), a separate module from `transaction.py` — analytics is a distinct concern from transaction CRUD): implements THIET-KE.md Part 4, all read-only, no writes. **Retrofitted 2026-07-26 from calendar months to `period.py`'s financial periods** — the highest-regression-risk change of the whole "hoạch định tương lai" expansion, since this is code that was already shipped and already fed the home-page alert banner; see `tests/test_risk.py` (17 cases, hand-computed expected values, including a real before/after spot check against the actual `data/finance.db`) before touching any of these functions again:
- `short_term_forecast()` (4.1): projected available balance at period-end = liquid balance − recurring still due this period (`get_remaining_recurring_this_period`, only counts `next_due` strictly after today, since anything due today-or-earlier is assumed already turned into a real transaction by `generate_due_recurring`) − projected variable spend (`get_average_daily_variable_spend`, averaged over the trailing 30 days — a rolling day-count window, **not** period-based, and correctly untouched by the retrofit — **excluding `source = 'recurring'` rows** so recurring commitments aren't counted twice) × days left in the period.
- `liquidity_risk()` (4.2) and `runway_months()` (4.3) both build on `get_average_period_essential_expense()` — the average essential (`categories.necessity = 'essential'`) spend per financial period over the last 3 *completed* periods that actually have essential spending (a period with none is **skipped, not counted as 0** — same semantics the old calendar-month version had via SQL `GROUP BY`, preserved deliberately: a genuinely-empty period silently dragging the average down would understate a safety-critical number). Returns `None`/`has_data=False` until there's at least one completed period of essential spending — never silently show a runway/liquidity number computed from zero history.
- `budget_balance_50_30_20(cursor, period_id)` (4.4): essential/optional spend vs. income for one financial period (identified by a `period.py`-shaped `period_id`, not a calendar month), grouped via `categories.necessity`.
- `get_reliable_monthly_income()` / `income_sustainability_margin()` (THIET-KE.md 3.7, built alongside the `income_sources` table, not part of the original Part 4 quartet): weights each active income source's `expected_amount` by its `reliability`, then compares that "chắc chắn" (certain) total against `get_average_period_essential_expense()` — a different question from `runway_months()`, which only asks how long *existing savings* last with zero income; this asks whether *ongoing* reliable income already covers the essential baseline. `has_data` is `False` until both at least one income source and one completed period of essential spending exist. Kept named/shaped as a **monthly** figure on purpose — `income_sources.expected_amount` is a stated user input independent of the period cycle, not a transaction-derived aggregate, so there was nothing here to retrofit.
- `get_budget_status(cursor, month)` — **deliberately NOT retrofitted, still calendar-month, still reads the old `budgets` table** (see the `budgets`/`period_budgets` bullets above). Superseded by `get_period_budget_status(cursor, period_id)` (reads `period_budgets` instead) for anything new, but kept working exactly as before — orphaned, not migrated in place, so no data is lost and nothing breaks for whatever still calls it (CLI menu 12–13 only, as of Mốc 1).
- `get_savings_rate_trend(cursor, periods=6, as_of=None)` (not in THIET-KE.md, added 2026-07-26 by direct request to make the risk report more grounded in real personal-finance theory, retrofitted to periods the same day as part of Mốc 1): unlike every other metric here, which is a single point-in-time snapshot, this returns the savings rate — `(income − expense) / income` — for each of the last `periods` *completed* financial periods that have any transaction at all (same "skip periods with no data" convention as the essential-expense average above), oldest-first, plus a `trend` of `"improving"`/`"declining"`/`"stable"`/`None` comparing the oldest to the newest period with a defined rate. The rationale (see the function's own docstring) is that *rate*, not the absolute amount saved, is what personal-finance literature treats as predictive of trajectory — none of the other metrics show direction of change over time, only current standing. Returns `{"periods": [...], "trend": ...}` — the key is `periods`, not `months`, and each entry's key is `period_id`, not `month` (renamed as part of the retrofit; every caller was updated to match).
- `suggest_period_budget_amounts(cursor, period_id)` / `get_period_budget_status(cursor, period_id)` (Mốc 1's new period-budgeting feature, see `period_budgets` above): the former is formula-based budget suggestion (b) of the three ways to set a budget — `categories.stability = 'fixed'` copies the previous period's budget for that category verbatim if one exists (falls back to the `'variable'` rule if there's no previous budget to copy yet); `'variable'` averages *actual spend* in that category over the last 3 completed periods, **treating a zero-spend period as 0, not skipping it** — the opposite convention from the essential-expense average above, and deliberately so: for "how much do I typically spend here," an unused category genuinely should pull the suggestion down, whereas for a safety metric like liquidity, a missing data point pulling the number down in the wrong direction is the failure mode to avoid. Categories with no `stability` set, or whose computed suggestion is 0, are skipped (nothing useful to suggest). `get_actual_spend_in_period(cursor, category_id, period_id, start_day)` is the shared per-category-per-period spend query both of these (and `web_app.py`'s `/api/ai/budget-suggestion`) call — public (no leading underscore) specifically because it has three real callers, not one.
- All accept an `as_of` override (defaults to `date.today()`) specifically so they're deterministic to test.
- Exposed via CLI menu option 9 (`show_risk_report`) and the web's `/risk` page — both call the exact same `risk.py` functions and just format the same numbers differently; don't duplicate the math in either UI layer.

**Screenshot import via Gemini** ([src/ocr_import.py](src/ocr_import.py), web-only — see below for why): the user's workflow is to add a clear note to every MoMo/MB Bank transfer, then upload screenshots. **This used to be local Tesseract OCR + regex line-parsing** (see git history around 2026-07-24) — that approach was replaced after Tesseract kept misreading real screenshots in ways plain regex couldn't recover from: garbled/dropped labels, and a two-column layout sometimes read as "all labels, then all values" instead of label-value pairs in order, each needing a new, increasingly fragile heuristic (`_find_labeled_note`, `_find_note_before_footer`, `_find_ascii_lowercase_note`, `_clean_mb_noi_dung`, `_find_mb_content_value`, junk-character filters, ... — all deleted when this was replaced). A vision model reads the screen semantically instead of line-by-line, so it isn't tripped up by OCR reading order.
- **This is a real, deliberate trade-off, not a free upgrade**: the original Tesseract choice was made specifically so screenshots of real financial data never left the user's machine. Switching to Gemini means those photos are now sent to Google's API. The user made this trade-off explicitly after Tesseract's accuracy problems proved hard to fix with more regex patches (see memory `project_stage2_progress`) — don't revert it back to local-only OCR without the user raising it again, and don't casually add *other* cloud calls elsewhere in the app on the assumption this precedent makes it fine.
- `analyze_image(image_bytes, mime_type)` sends the image straight to the Gemini API (`google.genai`, model configurable via `GEMINI_MODEL` env var, defaults to `gemini-flash-latest`) with a prompt asking it to return structured JSON (`response_mime_type="application/json"`, `response_schema=` a Pydantic model) — one `{amount, direction, note}` object per real transaction found in the image. This replaces the *entire* old regex pipeline in one call; there is no separate "raw OCR text" step anymore, and no per-screen-shape special-casing to maintain — the prompt itself explains what a "note" is vs. a bank reference code, and asks the model to skip balance-only lines and to not double-count a restated amount.
  - `gemini-flash-latest` (an alias, not a dated model name) was picked deliberately over pinning e.g. `gemini-2.5-flash` — that pinned name actually failed at runtime with a real key ("no longer available to new users"), confirming Gemini model names churn fast enough that hardcoding a specific version is a real reliability risk. Confirmed working end-to-end (correct amount/direction/note) against several test images with a real API key on 2026-07-24. If this alias ever breaks, check `client.models.list()` for what's currently available rather than guessing a name from memory.
- Requires `GEMINI_API_KEY` in the environment — checked lazily (only when `analyze_image` is actually called), so the rest of the app works fine without it; only the `/import` page needs it. Get a free key at [aistudio.google.com/apikey](https://aistudio.google.com/apikey).
- A light `(amount, direction)` dedupe still runs in Python after Gemini's response, as a defensive belt-and-suspenders check — the prompt already asks the model not to double-count, but this catches it if the model doesn't perfectly comply.
- `make_external_ref(amount, direction, note)` — since there's no bank reference number to key off, the dedupe key is a hash of `(amount, direction, note)`. Re-uploading the same screenshot produces the same hash, which collides with `transactions.external_ref`'s UNIQUE constraint; `web_app.py`'s `/import/confirm` catches `sqlite3.IntegrityError` per-row (committing after each successful insert, so one duplicate doesn't roll back the others in the same batch) and just skips that row. Unchanged from the Tesseract-era design.
- **Category is also AI-suggested, not just amount/direction/note**: `analyze_image` is given the full category tree (via `_format_categories`, built from `category_tree_as_json` for both kinds) as part of the prompt, and asked to return a `category_id` guessed from the *meaning* of the note (e.g. "tien gui xe" → a parking/transport category) — broader than `rules`' exact-substring matching. `analyze_image` validates any returned id against the real category set before trusting it (never take a model-generated foreign key on faith, even for a low-stakes field). In `web_app.py`'s `import_page()`, Gemini's guess wins; the existing `apply_matching_rule` (Stage 2's rules engine) is only consulted as a fallback when Gemini returns `null` (not confident enough to guess). Confirmed with a real API key across several notes — correctly distinguished categories like "Cà phê/Trà sữa" vs. "Ăn ngoài" vs. "Gửi xe" from note wording alone, and fell back sensibly (e.g. "Thu nhập khác") when no category was an exact fit.
- **Review happens before insert, not after**: `/import` (upload) → `analyze_image` per file → pre-fills a form per candidate (amount, direction, note, and now category) → user edits/deselects anything wrong → `/import/confirm` is what actually calls `insert_transaction(..., source="ocr", is_reviewed=0)`. Nothing extracted is ever written to the database without a human seeing it first — this safety property held under Tesseract and still holds under Gemini; don't remove it just because Gemini is more accurate.
- **Correcting the AI's category guess during review feeds the same "learn a rule" loop as correcting it after the fact** (2026-07-26, requested explicitly — the user didn't want the image-recognition categorization to stay "boxed in"/static as more screenshots come in): the review form (`IMPORT_REVIEW_TEMPLATE`) carries Gemini's original `suggested_category_id` per candidate in a hidden `suggested_{i}` field; in `import_confirm()`, if the category the user actually submits differs from that original suggestion (and a note exists), it calls the same `add_rule(..., created_from="learned")` used by `transaction.py`'s manual-edit flow — no separate consent checkbox, since consciously changing the dropdown already *is* the corrective action. This only strengthens the `apply_matching_rule` fallback layer, not Gemini's own guessing (Gemini is a stateless API call per image, not something this app fine-tunes) — so the practical effect is that **Gemini-null cases increasingly get caught by learned rules over time**, while cases where Gemini is confident but simply wrong stay AI-guessed each time unless that guess is later further corrected via the normal transaction-edit page too.
- This feature is **web-only, no CLI equivalent** — unlike everything else in this app, "upload a phone screenshot" only makes sense from a phone browser. Don't try to add a CLI menu option for it.
- **Shares its Gemini client and call-logging with `services/ai_client.py`, but deliberately not its caching/degradation contract** (2026-07-26, part of Mốc 1's AI infrastructure): `get_client()` (the API-key check + `genai.Client` singleton) and `log_call(...)` (writes one row to `ai_calls`) now live in `services/ai_client.py`, and `ocr_import.py` imports both rather than keeping its own duplicate `_get_client()`. `analyze_image()` gained an optional `cursor` parameter (passed by `web_app.py`'s `import_page()`) purely so it can call `log_call()` — its own `except Exception: raise` still propagates failures as a visible, blocking error, unlike `get_ai_suggestion()`'s "always degrade gracefully" contract, because OCR import's entire point disappears if the image can't be read; there's no sensible "page still works, just no AI opinion" fallback for it the way there is for an advisory task. `import_page()` in `web_app.py` explicitly `conn.commit()`s in both its success and exception paths specifically so these `ai_calls` log rows (and `apply_matching_rule`'s `hit_count` bumps during the preview step) actually persist — before this fix they were silently rolled back on `conn.close()` with no pending commit, a real (if low-severity) gap fixed alongside adding the logging.

**AI infrastructure** ([src/services/ai_client.py](src/services/ai_client.py) + [src/prompts/](src/prompts/), added 2026-07-26 for the "hoạch định tương lai" expansion): the **one** shared entry point for every AI-generated recommendation/explanation across Mốc 1–5 (budget suggestions today; goal prioritization, spending-simulation advice, seasonality explanations, macro-context summaries, and daily summaries as later milestones land) — explicitly **not** used by `ocr_import.py`'s `analyze_image()`, which is a structurally different task (see above).
- `get_ai_suggestion(cursor, *, task, input_data, response_schema, prompt, model=None, ttl_seconds=...)` **never raises**. It always returns either `{"available": True, "data": <dict>, "cached": bool}` or `{"available": False, "reason": "no_key"|"quota"|"timeout"|"invalid_response"|"network", "data": None}` — the same "sentinel dict, not `None`, not an exception" idiom `risk.py` already uses (`runway_months` returns `{"months": None, ...}`, not `None`), chosen specifically so every template can branch on `{% if ai.available %}` uniformly. `response_schema` is a Pydantic model class — Gemini is forced into matching JSON (`response_mime_type="application/json"`), never parsed from free text, enforcing the standing rule that **AI never computes money**: `input_data` must already contain every number the task needs, computed by plain Python beforehand; the AI only interprets/prioritizes/explains numbers it's handed.
- **Caching**: keyed by `sha256(json.dumps({"task": task, **input_data}, sort_keys=True))` in `ai_cache`, filtered by `expires_at > datetime('now')` (default TTL 6 hours). A cache hit is **not** logged to `ai_calls` (it made no API call, used no tokens — logging it there would misrepresent what that table tracks); a failure is **not** written to `ai_cache` (so it doesn't "poison" the cache and block a retry for the rest of the TTL window). This is also how a "call at most once per day" feature (planned for Mốc 5's daily summary) falls out for free, with no special-case code: folding `date.today().isoformat()` into that task's `input_data` makes the cache key change once a day on its own.
- **Graceful degradation is structural, not just try/except**: every AI-powered feature is meant to be called from a separate `/api/ai/<task>` JSON endpoint, fetched client-side via `fetch()` **after** the page's own Python-computed numbers have already rendered (a lightweight "Đang phân tích…" placeholder meanwhile) — so a page can never fail or stall because Gemini is slow or unreachable, which matters concretely since PythonAnywhere's free tier may block outbound calls to Gemini's domain entirely (unconfirmed as of Mốc 1 — the first live smoke test against a real deployed host is still owed, see below).
- **Model defaults were deliberately NOT set to the literal names originally requested** (`GEMINI_MODEL` → `gemini-2.5-flash`, `GEMINI_MODEL_HEAVY` → `gemini-2.5-pro`) — `gemini-2.5-flash` is the exact pinned name that already 404'd at runtime with this project's real API key (see `ocr_import.py`'s own history above), so `DEFAULT_MODEL`/`DEFAULT_MODEL_HEAVY` default to the alias family already proven to work instead: `gemini-flash-latest` / `gemini-pro-latest`. The env var names themselves are exactly as requested — only the *fallback value* when they're unset changed. **This needs a live smoke test with a real `GEMINI_API_KEY` before anything is built on top of `GEMINI_MODEL_HEAVY` for Mốc 3/4** — `gemini-pro-latest` has never actually been called successfully yet, unlike the flash alias.
- **A real, easy-to-hit bug found and fixed while wiring this up**: `.env.example` ships several keys with an empty right-hand side (`SECRET_KEY=`, `GEMINI_MODEL=`, ...) so users see the full list of what's configurable. But `os.environ.get("KEY", default)`'s default only fires when the key is **completely absent** from the environment — `python-dotenv` loading `KEY=` from a `.env` file sets it to `""`, which is present-but-empty, so the fallback silently never triggers and code gets an empty string instead of its intended default. This broke `app.secret_key` outright (crashed every login with "the session is unavailable because no secret key was set") and would have silently broken `GEMINI_MODEL`/`GEMINI_MODEL_HEAVY` (Gemini calls with an empty model name) the same way. Fixed everywhere by switching from `os.environ.get(KEY, default)` to `os.environ.get(KEY) or default` — **use this pattern for any future optional env var with a non-empty default**, not the two-argument form, given `.env.example` will keep shipping blank-by-design optional keys.
- Prompt templates live as plain `.md` files in `src/prompts/` (one per task, e.g. `budget_suggestion.md`), loaded and `.format(**context)`'d by the calling route — kept out of Python source specifically so a prompt can be tuned without touching code, per the user's own requirement.

**Balance maintenance**: all writes go through `insert_transaction()` in `transaction.py`, which inserts the row and adjusts `accounts.current_balance` in the same call — there's no trigger. Any new code path that inserts into `transactions` must call this function rather than writing its own INSERT. Symmetrically, `delete_transaction(cursor, transaction_id)` looks up the row's `amount`/`direction`/`account_id` before deleting it and applies the *inverse* balance delta — the only sanctioned way to remove a transaction; it returns `False` (no-op) rather than raising if the id doesn't exist. Used by the web's `/transactions/<id>/delete` (CLI has no delete — it was requested web-only). It also nulls out any `behavior_events.transaction_id` pointing at the row before deleting it (found and fixed 2026-07-26 during a self-review pass) — that FK has no `ON DELETE CASCADE`, so deleting a transaction that had ever been category-edited (which logs a `category_overridden` event) would otherwise fail with a foreign key violation; the event row itself is kept, just detached, since it's still meaningful analytics on its own.

**Shared core vs. CLI vs. web** ([src/transaction.py](src/transaction.py)): the file has two halves, marked by `# ----` section comments. The data-layer half (`get_active_accounts`, `get_categories`, `insert_transaction`, `get_recent_transactions`, `get_transaction_by_id`, `delete_transaction`, `update_transaction_category`, `log_behavior_event`, `get_monthly_totals`, `get_income_sources`, `add_income_source`, `get_budgets`, `set_budget`, `get_period_budgets`, `set_period_budget`, `get_event_templates`, `get_event_template_items`, `create_event_plan`, `add_event_plan_item`, `get_event_plans`, `get_event_plan_items`, `get_rules`, `add_rule`, `delete_rule`, plus the rest of the rules/recurring functions) has no `input()`/`print()` and is imported by both the terminal CLI further down in the same file and by `web_app.py`. **Web form** ([src/web_app.py](src/web_app.py)): a Flask alternative to the CLI, for using the tracker from a phone browser instead of the terminal. Routes mirror the CLI's transaction-related menu options plus several additions that only exist on the web: `/` (add transaction — the only one that's a JS single-page form posting to `POST /api/transactions` via `fetch()`, so it never reloads), `/transactions` (recent list; each card has a **Sửa** link to `/transactions/<id>/edit` and a **Xóa** button — a plain POST form to `/transactions/<id>/delete` with a JS `confirm()` guard, calling `delete_transaction()` so the account balance is reversed correctly, then redirecting back), `/summary` ("Tổng quan" — current-month income/expense/difference plus every active account's balance; no month-picker, unlike the old version, since the redesign brief only asked for the current month), `/rules` (lists every row from `rules` — pattern, category, priority, hit count, and whether it was user-added or learned from a correction — each with a **Xóa** button posting to `/rules/<id>/delete`; this is the *viewing* half of Stage 2's auto-categorization system finally getting a web UI, since adding rules already worked implicitly via the "learn from correction" flow on the edit page), `/risk` (the risk metrics from Part 4 plus income sustainability and the "Hũ chi tiêu" budget-status bars, read-only), `/import` + `/import/confirm` (OCR screenshot import — the CLI has no equivalent, see above), **`/budgets` + `/budgets/save`** (Mốc 1, 2026-07-26 — period-based budgeting: each expense category shows an editable amount pre-filled with either an existing `period_budgets` row or a formula suggestion from `risk.suggest_period_budget_amounts()`, a colored progress bar — green/amber/rose via a `bar_color` class computed server-side from `pct_used` — once a budget exists for that category, and prev/next arrows to browse other periods via `?period=<period_id>`; `/budgets/save` upserts every submitted `amount_<category_id>` field via `set_period_budget(..., source="manual")`, silently skipping blank/zero/invalid-category-id fields rather than erroring), **`/goals` + `/goals/new` + `/goals/<id>`** (Mốc 2, 2026-07-26 — list/create/detail for `goals`, progress bars colored by `is_overdue`/`is_off_track`/on-track same three-tier scheme as budgets, `/goals/new`'s JS auto-fills the target field from `risk.suggest_emergency_fund_target()` only when "Quỹ khẩn cấp" is picked and the field is still empty), **`/events` + `/events/new` + `/events/<id>` + `/events/<id>/dismiss-goal-prompt`** (Mốc 2 — the first web equivalent for event-plan creation, previously CLI-only; `/events/<id>?suggest_goal=1` is how the goal-prompt banner described above actually surfaces), **`/simulate` + `/simulations` + `/simulations/<id>`** (Mốc 3, 2026-07-26 — spending-decision simulator: `/simulate` is the input form, reachable via a plain text link from `/transactions` or via `/`'s ≥1,000,000đ interstitial `confirm()`; `/simulations` is the saved history; `/simulations/<id>` shows the Chart.js comparison chart + all 6 scenarios + the AI recommendation, described fully under "Spending-decision simulation" above), **`/forecast` + `/forecast/<id>` + `/forecast/<id>/macro-scenario`** (Mốc 4, 2026-07-26 — cashflow forecasting, reachable via a plain text link from `/risk`; described fully under "Cashflow forecasting" above). Recurring and income-source *management* (creating/listing them — CLI menu 6–7, 10–11) still has no web equivalent — extend the web app only if asked; the data they produce already shows up on these pages regardless of which interface created it, since both read the same tables.
- **Two design systems coexist by deliberate, incremental choice, not inconsistency**: `/transactions`, `/summary`, `/rules`, `/budgets`, `/goals` (+ its sub-pages), `/events` (+ its sub-pages), `/simulate`/`/simulations` (+ its sub-pages), and `/forecast` (+ its sub-pages) use Tailwind CSS loaded from the Play CDN (`<script src="https://cdn.tailwindcss.com">`, no build step) — `TAILWIND_HEAD` (head boilerplate + a `tailwind.config` extending a `brand` color that matches the PWA icon's `#007aff`) and `tailwind_nav(active)` (a plain Python function, not Jinja, building the segmented-pill nav — "Nhập"/"Danh sách"/"Tổng quan"/"Ngân sách"/"Mục tiêu"/"Luật" — since which link is active never depends on request data) are shared constants/helpers in `web_app.py`, concatenated into each of those templates the same way `BASE_STYLE` is. None of `/events`, `/simulate`/`/simulations`, or `/forecast` get their own nav slot — `/events` reuses `tailwind_nav("goals")` (reached via a text link from `/goals`); `/simulate`/`/simulations` and `/forecast` each pass an active key ("simulate", "forecast") that matches nothing in the nav so nothing highlights, reached via plain text links (from `/transactions` and `/risk` respectively, or from `/`'s ≥1,000,000đ prompt for `/simulate`) — all deliberate, to avoid overcrowding the nav further; **if a later milestone wants any of these more prominent, add a nav slot deliberately then, don't assume it needs one now.** `/`, `/risk`, `/import`, `/import/confirm`'s review screen, and the edit-transaction page still use the original inline `BASE_STYLE` CSS and the older nav (`Thêm`/`Danh sách`/`Tổng quan`/`Sức khỏe TC`/`Nhập ảnh`/`Luật`/`Ngân sách`/`Mục tiêu` — 8 links, wraps across rows via `flex-wrap` with each link at `flex: 1 1 30%`; `/simulate` and `/forecast` have no slot here either, same reasoning). **Don't merge these into one system without being asked** — the split exists because the user asked for the Tailwind redesign one step at a time and explicitly scoped it to specific pages each time; migrating the rest is a separate, not-yet-requested decision. **This nav is at its practical limit** — Mốc 5's health-score dashboard is expected to restructure navigation entirely (see the original plan's own risk callout); don't keep adding top-level links without reconsidering the nav shape first.
- HTML/CSS/JS is inlined via `render_template_string` for every page — no `templates/` folder.

**PWA / "Add to Home Screen" on iPhone**: [src/static/](src/static/) is the **one** static-assets folder in the project (everything else is inlined via `render_template_string`) — it exists only because Flask's built-in static file serving is the simplest way to serve `manifest.json` and the app icons, and `before_request`'s auth check already excluded the `"static"` endpoint from day one (needed since a browser fetches these before any session exists). Icons (`apple-touch-icon.png` 180×180, `icon-192.png`, `icon-512.png`, `favicon.png` 32×32) are a plain blue square with a white "đ" glyph, generated once with PIL (not a runtime dependency — Pillow isn't in `requirements.txt`; these are just committed image files). Every page's `<head>` links `manifest.json` and sets `apple-mobile-web-app-capable`/`apple-mobile-web-app-title`/`theme-color` so tapping Safari's "Thêm vào MH chính" (Add to Home Screen) produces a standalone-look icon instead of a bare bookmark.

**Auth on the web form**: single shared password, not per-user login (deliberate — see memory `project_web_form_multiuser_phase`: the goal right now is letting many people log transactions with minimal friction, not tracking who entered what). `APP_PASSWORD` is read from the environment and never hardcoded — the app refuses to start without it. A Flask session cookie (`session["authenticated"]`), valid 30 days, gates every route via a `before_request` hook except `/login`; `/api/*` returns 401 JSON instead of a redirect when unauthenticated. `SECRET_KEY` may also be set via env; if omitted it's a random value generated per-process, meaning all sessions invalidate on every restart — acceptable for this use case, don't "fix" it without being asked. Once deployed somewhere persistent (see below), `SECRET_KEY` should actually be set to a fixed value, otherwise every worker restart on the host logs everyone out. `LOGIN_TEMPLATE`'s password `<input>` has `autocomplete="current-password"` specifically so the browser (Safari Keychain on iPhone) offers to save/autofill it — a small, deliberate friction reduction so re-entering the shared password isn't a recurring tax on every visit.

## Code conventions actually in use

- Function/variable/constant names and comments across `transaction.py`, `seed_data.py`, `init_db.py` are in **English**, per docs/THIET-KE.md Part 6. User-facing text passed to `print()`/`input()` stays in **Vietnamese** — that's the target audience's language, not a convention to migrate away from.
- Money is always stored as integer VND (no decimals).
- Timestamps are stored as `TEXT` via `datetime.now().strftime("%Y-%m-%d %H:%M:%S")` / SQLite `datetime('now')`.
- **`tests/` (added 2026-07-26) is stdlib `unittest` only** — no `pytest`, no fixtures framework, matching the rest of the project's "standard library first" bias. Reserved for genuinely money-math-shaped logic where a hand-computed expected value is worth writing down permanently (`period.py`'s date boundaries, `risk.py`'s retrofitted period metrics) — not a blanket requirement to test every function; most of this codebase is still validated the established way, via a scratchpad-copy-of-`data/finance.db` smoke test before touching real data, not a permanent test file.
