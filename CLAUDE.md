# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A personal finance tracker ("Quản lý tài chính cá nhân") built as Python + SQLite, usable from either a terminal CLI or a Flask web form. The project follows the 7-stage roadmap in [docs/THIET-KE.md](docs/THIET-KE.md) (Vietnamese design doc — read it before making schema or product-behavior decisions, it is the authoritative spec). **Stage 1** and **Stage 2** (auto-categorization, recurring transactions, learn-a-rule-from-correction) are fully built. **Stage 6** (Part 4's risk metrics, Part 1.3's proactive alerts, Part 3.7's income sources, and Part 3.8's event planning) and the **Stage 4** screenshot import are also built, all picked up out of roadmap order, deliberately: risk metrics and alerts needed no external data; income sources and event planning were requested directly, inspired by looking at MoMo/Timo's own features (see memory `project_stage2_progress`); screenshot import (`/import` in the web app, [src/ocr_import.py](src/ocr_import.py)) is now powered by the Gemini API's image understanding rather than local OCR, after local Tesseract's accuracy on real screenshots proved hard to fix with regex (see the file's own module docstring and CLAUDE.md's Architecture section for the full story). **Stage 3 (auto-reading MB Bank emails) was skipped, not just deferred** — the user found it's blocked by iOS email-access restrictions, so screenshot import (Stage 4) became the real path for semi-automated import instead. Stage 7 (investments/gold/FX) still has no logic — only a schema-only placeholder table (see below). `budgets` (category-level "Hũ chi tiêu" budgeting) also isn't in THIET-KE.md at all — added by direct request, inspired by Timo, not part of the original design; **now itself superseded by `period_budgets`** (see below), kept around unwritten-to rather than dropped. **The web UI is now a deliberate two-tier mix, not uniformly plain**: `/transactions`, `/summary`, `/rules`, and `/budgets` use Tailwind CSS (via CDN, see below) per a detailed visual brief from the user (generous whitespace, large touch targets, amount as the most visually prominent element, calm/neutral palette, no default-template look); `/`, `/risk`, `/import`, and the edit-transaction page are still the original plain inline-CSS design (`BASE_STYLE`) and were explicitly left alone in that same request, one step at a time, not because they were forgotten.

**2026-07-26: a second, much larger expansion beyond the original 7-stage roadmap began** — moving the app from "ghi nhận quá khứ" (recording the past) to "hoạch định tương lai" (planning the future), the user's own framing. Requested as 5 sequential milestones under one approved plan, executed one after another with a short report at the end of each (not waiting for per-milestone approval): **all 5 milestones are done** — Mốc 1 (period-based budgeting + AI infrastructure), Mốc 2 (financial goals), Mốc 3 (spending-decision simulation), Mốc 4 (cashflow forecasting), and **Mốc 5 (health-score dashboard, now living at `/`)** — see the dedicated sections below (`period.py`, `services/ai_client.py`, migrations, `/budgets`, `goals`, `/goals`, `/events`, `spending_simulations`, `/simulate`, `cashflow_forecasts`, `/forecast`, "Health-score dashboard"). The single biggest structural change Mốc 1 made: **every period-shaped calculation in the app now uses a configurable financial period (default the 15th of one month through the 14th of the next) instead of the calendar month** — see `period.py` below; this was a deliberate retrofit of already-shipped `risk.py` code, not just new code, because the user was explicit that "every period-based calculation must use this cycle, not the calendar month." **Mốc 5's own biggest structural change: `/` is no longer the add-transaction form** — that form moved to `/add`; `/` is now the health-score dashboard, the new "first thing I look at every day" home page (the user's own framing of their daily habit loop: see balance → know where I stand → enter today's transaction → see the plan). Any doc, memory, or mental model that still says "`/` is the add-transaction page" predates this change.

**2026-07-27/29: a product-hardening pass beyond the 5-milestone plan** — not a new milestone, but a from-scratch self-review the user explicitly asked for ("tự tạo giả định khi người dùng sử dụng sản phẩm để tìm các lỗi... tạo ma sát khiến người dùng rời bỏ") to find real bugs/friction by simulating actual usage, close essential-feature gaps, deepen cross-feature integration, and integrate AI more deeply — see "Amount parsing and form-error UX", "Account transfers", and the updated "Health-score dashboard"/"AI infrastructure" sections below for what changed. Two findings drove most of the work: (1) every money-amount text field across the web app silently mishandled anything that wasn't bare digits — worst case, typing the everyday Vietnamese shorthand "1tr" into the **add-transaction form itself** got live-reformatted keystroke-by-keystroke down to just "1" (1 đồng instead of 1,000,000), with zero warning, confirmed live before being fixed; (2) `categories.kind = 'transfer'` had been seeded since Stage 1 but no CLI/web screen ever exposed it, so moving money between the user's own accounts (topping up MoMo, an ATM withdrawal, paying off a credit card) had no correct way to be recorded without silently inflating income/expense totals.

**[sheet-lite/](sheet-lite/) — a second, deliberately separate product living in this same repo, and as of 2026-08-01 the one the user is actively developing.** Google Sheets as the database + a Google Apps Script Web App as the API layer (a static page can't safely write to a Sheet directly — no way to embed write credentials in public client-side code) + a static frontend with no build step, served from GitHub Pages at `https://aodtsix-cmd.github.io/quan-ly-tai-chinh/sheet-lite/`. Chosen over bolting Sheets export/import onto the Flask app because the user explicitly asked for "1 file html để up github và phát triển dần" — something a server-dependent app can't be. It deliberately mirrors the main app's core data model (accounts/categories/transactions, `amount` always positive + `direction` carrying the sign, transfers tagged with a `kind=transfer` category) so it can keep absorbing this app's features without a data-model rewrite. **[sheet-lite/README.md](sheet-lite/README.md) is the authoritative doc for setup, the sheet schema, and how to edit the code — do not duplicate that detail here.** The two apps **do not share data**; they are two separate ledgers.

**v3 (2026-08-01)** was a full rebuild in response to "triển khai và tôi có thể dễ sửa code rồi lấy link và sử dụng dần... kết hợp với claude design để thiết kế, tích hợp các chức năng tôi phát triển như trong file claude.md" — i.e. make the static version the real product, designed properly, carrying the Flask app's feature set.
- **No longer one HTML file.** v1/v2's single `index.html` was ~700 lines and would not survive this feature set. Now `index.html` (shell + the add-transaction form as static markup) plus `assets/app.css`, `assets/core.js` (config/API/formatting/amount parsing), `assets/views.js` (pure HTML-string render functions), `assets/app.js` (state, tab routing, delegated event handling, client-side spending simulation). **Plain `<script src>` tags, NOT ES modules** — deliberate, so the page still works opened directly over `file://`. Splitting the files directly serves the user's "dễ sửa code" requirement; don't collapse it back into one file.
- **Five-tab mobile shell** (Nhà / Nhập / Sổ / Kế hoạch / Cài đặt) with a fixed bottom tab bar, replacing v2's single scrolling stack of cards. Views are re-rendered wholesale from `App.state.data`, which is why every click goes through **one delegated `document` listener** rather than per-element bindings — rebinding after each render was the alternative and it is much easier to get wrong.
- **The add-transaction form is the one thing never re-rendered** (only its `<select>` options are refreshed). Wiping a half-typed amount on a background refresh is exactly the friction this app exists to remove.
- **Design system** (`app.css`): a slate-indigo brand colour chosen to *recede* so the semantic money colours (brick `--out`, pine `--in`, steel `--transfer`, ochre `--warn`) are the loudest thing on screen; every figure is set in a tabular monospace (`.num`, `--font-num`) while prose stays in the system UI face — that split is the app's typographic identity and also gives full Vietnamese diacritic coverage with no webfont to download. Both themes are defined at token level under `:root`, `@media (prefers-color-scheme: dark)`, and `:root[data-theme=...]` (the in-page toggle must beat the media query in both directions). **The signature element is the "dải kỳ" (period ribbon)**: two tracks on one scale, time-elapsed above money-spent, so the gap between them *is* the reading — it only makes sense in an app organised around a 15th-to-14th cycle rather than a calendar month, which is the point.
- **Charts are hand-built inline SVG** (`App.sparkline`, `App.lineChart`) — no Chart.js, unlike the Flask app's `/simulations/<id>`. Two small shapes didn't justify a CDN dependency on a page whose whole selling point is that it has none.
- `Code.gs` roughly doubled. New over v2: `actionSetup_` (creates missing tabs and repairs short header rows from older versions, optionally seeding the same accounts/category tree as `seed_data.py` — this replaced the old "create 5 tabs by hand" setup step **and** is the upgrade path for an existing Sheet); a `Recurring` tab with `generateDueRecurring_` running on every bootstrap (mirrors `generate_due_recurring`, idempotent within a day, catches up on missed periods up to `RECURRING_CATCHUP_LIMIT`); a `Rules` tab with `findMatchingRule_`/`resolveCategoryFromRules_` (mirrors `apply_matching_rule`); `update_transaction` and backdating via `occurred_at` (v2 could only delete-and-retype, and always stamped "now"); the Mốc 5 metric set (`getHealthScore_`, survival days, financial rigidity, burn rate vs elapsed, current-period savings rate, spending concentration with parent rollup, income stability, budget streak, net worth, savings-rate trend, 50/30/20); `suggestPeriodBudgetAmounts_`; `actionExportCsv_`; `actionGetAiAdvice_`. Routing moved from an if-chain to read/write action maps, with writes still wrapped in the script lock.
- **Still deliberately simpler than the Flask app**, and the `Code.gs` header comment is the list of record: the forecast is `project_simple_trajectory` only (no seasonality, no macro context, nothing persisted), simulations are computed client-side and never saved, and there is no `behavior_events`, no event plans, no OCR import, and **no AI response cache** (`ai_cache`'s equivalent) — calls are user-initiated or once per page load, which stays inside the free tier.
- **The spending simulator surfaces WHEN each option breaks, not just how low it gets.** Found live during this build: over a full 12 periods every scenario spends the same total, so their lowest balances converge and the comparison table said nothing. It now reports the first period each scenario goes negative, and lists the no-purchase baseline as a row alongside the options — if the trajectory is already breaking without the purchase, "red" everywhere means something quite different.
- **Backward compatibility with an already-live Sheet stayed a real constraint.** `getSheetOptional_` is used for every optional tab in `actionBootstrap_`, so a Sheet built by v1/v2 still loads (missing features just read as empty) instead of every page load throwing and the whole app going dark. Write actions still use the hard-throwing `getSheet_`, so actually *using* a missing feature gives a clear error rather than silently no-op'ing. Covered by its own regression test.
- **Test suite grew from 33 to 73** (`apps-script/test/test_code.js`, plain `node`, no real Sheet or deployment — stubs the Apps Script globals with an in-memory fake). The harness gained `insertSheet` and multi-cell `setValues` for `actionSetup_`. New coverage: setup/seeding/header repair, recurring generation and idempotency, rule matching and priority, `update_transaction`'s balance reversal across amount/direction/account changes, health-score downgrades, net worth vs liquid balance, 50/30/20, concentration rollup, rigidity, CSV quoting, and the dispatch layer's error envelope. **Verification during this build went further than the unit tests**: `scratchpad/mock-server.js` ran the real `Code.gs` under Node behind an HTTP server serving the real frontend, so the whole app was clicked through end to end (including a live write that auto-categorised via a rule) before anything shipped. That harness is scratchpad-only and not committed — rebuild it if a future pass needs the same confidence.
- **`index.local.html` (gitignored, never committed)** was v2's personal pre-filled copy with a real URL+token baked in. **v3 has no equivalent and doesn't need one** — the connection is entered once and kept in `localStorage`, and the committed `index.html` always ships blank. Never put real credentials in it; this repo's Pages site is public.
- **v3.2 (2026-08-01, same day) made setup self-driving**, after the user said they'd lost track of their old Sheet and wanted "tạo 1 sheet mới có app script tạo sẵn các sheet để tôi chỉ việc dán vào" plus the least possible ongoing breakage. I cannot create a Sheet in their Google account, so the code creates itself instead: `setupEverything()` (public, no trailing underscore so it appears in the Apps Script Run dropdown) builds every tab, seeds the category tree, pins the timezone, **generates and displays an `APP_TOKEN`** so nothing has to be typed into Script Properties by hand, and an `onOpen()` custom menu ("Sổ tài chính": Thiết lập / Xem mã kết nối / Kiểm tra) repeats all three from the spreadsheet itself. `actionBootstrap_` additionally **self-heals**: `needsSetup_()` triggers a locked, re-checked `actionSetup_({seed:1})` when a tab is missing or Categories is empty, so even skipping the setup step entirely still yields a working app on first page load. Setup went from "create 7 tabs by hand + set 3 script properties + set the timezone" to "paste, run one function, deploy".
- **The script-project timezone is no longer depended on at all.** It lives in `appsscript.json`, can't be set from code, and getting it wrong silently shifts every date by a day. `getTimeZone_()` reads the *spreadsheet's* timezone (which `actionSetup_` pins to `Asia/Ho_Chi_Minh`) with a hardcoded fallback; `Session.getScriptTimeZone()` has zero remaining callers — **don't reintroduce it.**
- **`VERSION` + `health_check`** exist specifically because Apps Script's worst failure mode is silent: redeploying without picking "Phiên bản: Mới" keeps serving the old code with no error anywhere. The running version is shown in Cài đặt, and `actionHealthCheck_` returns a per-item checklist (each tab, accounts, categories, a transfer category, necessity coverage, timezone, Gemini key) rendered as pass/fail so a problem names itself instead of surfacing as a generic failure three screens later. The Gemini row is deliberately marked optional rather than failing.
- **Two real frontend bugs were found by driving the app, not by reading it** — both invisible to the Node suite, which only covers `Code.gs`:
  - **`form.id` was shadowed.** A form's named controls are exposed as properties on the form element, so `<input name="id">` in the edit-transaction and edit-account dialogs made `form.id` return that input rather than `"edit-form"`. Every `form.id === "..."` comparison failed, no branch ran, `preventDefault()` was never called, and submitting did a **real GET navigation with the whole form in the query string**. Both edit dialogs were completely dead. Fixed by reading `form.getAttribute("id")` — **never use `form.id` for this**, and the comment in `app.js` says so.
  - **Every transaction saved twice.** `#tx-save` is `type="submit"` and was *also* listed in the delegated click-handler selector, so one click ran `submitTransaction()` directly and again via the form's own submit event. Fixed by removing it from the click path; the submit event is the single route (and it covers pressing Enter in a field too).
- **The AI refuses to comment on an empty ledger** (`actionGetAiSummary_` returns `reason: "no_data"` when `transaction_count === 0`). Caught by loading a blank sheet and watching the model confidently describe spending that did not exist — the exact failure this project's AI rules exist to prevent. The dashboard also swaps to a first-run card (`renderFirstRunCard`) instead of a grid of dashes when there are no transactions.
- Also folded in during this pass: the **50/30/20 card** (`balance_50_30_20` was already computed by v3 and simply never rendered) and **learn-a-rule-on-correction** — changing a category in the edit dialog reveals an offer to save that description as a `Rules` pattern (`created_from: "learned"`), mirroring the Flask app's own correction loop and closing the gap that the Rules tab could otherwise only be filled in by hand. Test suite 73 → 84.
- **v3.3 (2026-08-02) added income sources and event plans, and wired them into everything already there** — the user asked for these two by name plus "hệ thống phải có tính liên kết chặt chẽ với nhau", so each one was landed with its cross-references rather than as another isolated screen. `IncomeSources` (`id, name, expected_amount, reliability, is_active`) mirrors THIET-KE.md 3.7: `reliability` 0–100 is what lets `getReliableIncomePerPeriod_` discount a 40%-certain side gig, and `getIncomeSustainability_` compares that discounted total against `getAverageEssentialExpensePerPeriod_` — a different question from runway, which asks how long savings last with *no* income. `EventPlans` + `EventPlanItems` mirror 3.8, including its rule that a template suggests **item names only, never a price** (`EVENT_TEMPLATES` is a plain constant, no sheet). The integrations are the point: the forecast subtracts each event's **unpaid remainder** in the period the event actually falls in and can swap historical average income for reliability-weighted income (`income_basis_reliable`); the dashboard gained a "Thu chắc chắn" tile and a nearest-event card that cross-checks the event against today's liquid balance; the AI daily summary now sees income margin and the nearest event and is asked to connect them; and a big-enough, far-enough event offers to become a `goal`, creating it and linking back via `link_event_to_goal` so the offer never returns. Test suite 84 → 102.
- **`event_total` is summed from the periods actually projected, not from every future event.** Found while reading the forecast output: three planned events totalled 56tr but only 8tr fell inside the 6-period window, so the footnote claimed money had been subtracted from a chart it never touched.
- **A blank white app was the worst bug of the whole build, and it was in the error path.** The user opened the live site and got a page with only the top bar and tab bar. Cause: a stale `localStorage` connection (same origin, same key) pointing at an older deployment whose `bootstrap` payload has no `period`/`money`/`health`, so `renderHero` threw mid-render; the throw escaped, and `App.load`'s own catch then called `switchTab` which re-rendered and threw again. Three fixes, all verified against a fake old-shaped backend: `App.showLoading()` paints before the first round trip (an Apps Script call takes seconds, and a dead URL hangs forever); `App.load` shape-checks the payload and names the real problem ("mã trên Google Sheet cũ hơn giao diện") with the exact redeploy steps; and `renderCurrentTab` wraps rendering in try/catch, routing any throw to `App.showFatal`, which parks the message in `App.state.fatalHtml` so it survives a tab switch instead of being wiped by a re-render. **Never let a render failure resolve to an empty view** — the screen going blank reads as total breakage and gives the user nothing to act on.
- **A root `index.html` redirect was added at the repo root.** GitHub Pages serves this repo from `/`, so the URL shown in Settings → Pages was a bare 404 while the app sat in `/sheet-lite/` — which reads as a broken deployment. Pages can't do server-side redirects, so it's the standard meta-refresh + `location.replace` + visible fallback link.
- **v3.4 added an unauthenticated `version` action, and it exists to solve a real support dead-end.** The user pasted the correct 2,338-line v3.3 `Code.gs` and still got "mã cũ" from the app, because Apps Script serves the **deployed version**, not the editor's contents — pasting and saving changes nothing until you edit the deployment and pick "Phiên bản: Mới", and that failure is completely silent. Diagnosing it through any authenticated call is impossible: a stale deployment rejects `checkToken_` before it can identify itself. So `handle_` answers `action=version` **before** the token check, returning nothing but the build number, which means the URL can be pasted straight into a browser (`…/exec?action=version`) to see what is actually live. The frontend calls it when the payload shape check fails, so the error names the real gap ("đang chạy bản cũ hơn v3.4 · giao diện cần v3.4") and lists the five redeploy steps inline. Tests assert the action needs no token, leaks only `version`, and that every other action still requires one. Line counts are a useful second signal and are recorded in the README: v2 = 909, v3.0 = 1816, v3.2 = 2053, v3.4 ≈ 2350.
- **`App.parseResponse` exists because Apps Script returns HTML with a 200.** Probing a freshly-created deployment live, two consecutive calls returned Google's "Không tìm thấy trang" page before the third returned JSON — the deployment was still propagating. `response.json()` on that throws `Unexpected token '<'`, which is meaningless to a user, so both verbs now read text first and, on a parse failure that starts with `<`, say what it actually means (wrong URL / deleted deployment / just deployed, wait a minute).
- **The loading state escalates because a real cold start took 97 seconds.** Measured on that same deployment; every subsequent call was under a second. A frozen "Đang tải" for a minute and a half is indistinguishable from a hang, so `App.LOADING_HINTS` moves 0s → 6s → 45s, and the timers stop as soon as `App.state.loading` clears.
- **v3.5 ported screenshot import**, the one Flask feature that matches the user's actual daily habit (add a note to every MoMo/MB transfer, then screenshot it). `actionAnalyzeImage_` sends the image to Gemini as an inline `inline_data` part alongside the category tree and asks for a JSON array; `actionImportTransactions_` is the only thing that writes, and it runs solely on rows the user confirmed. **Review-before-insert is the load-bearing safety property** — an image never writes straight into the ledger, and there's a test asserting `analyze_image` leaves both the Transactions sheet and the account balance untouched. `external_ref` (new, additive column; `ensureHeader_` adds it to existing sheets) is an MD5 of amount+direction+note, so re-uploading the same screenshot reports "đã nhập trước đó" instead of double-recording. Each row in a batch is independent: a bad amount or a missing account skips that row and the rest still save. **Extraction quality is UNVERIFIED against a real screenshot** — no `GEMINI_API_KEY` was available while building it (the repo's `.env` has the key blank) — so the whole design assumes the read may be wrong and makes that cheap to fix; the request shape, fence-stripping, dedupe, invalid-category rejection and batch behaviour are all unit-tested against a stubbed `UrlFetchApp`. The browser downscales to 1280px on the long edge before upload, because a phone photo would otherwise blow past Apps Script's payload limit.
- **The amount parser now reads all the digits after `tr` as a fraction**, not just one: `2tr5` = 2.5tr as before, but `1tr25` = 1.25tr and `1tr250` = 1.25tr, which is how people actually type. Found by a test that used `1tr25` as an ordinary value and got a parse error. **This diverges from the Flask app's `parse_amount_vnd`, which still accepts only a single trailing digit** — sync it if that app is ever picked up again.
- **The connection form verifies a URL before saving it.** The user went through several redeploy rounds where the app kept reporting old code, because "Bản triển khai mới" mints a *new* URL while the app stayed pointed at the previous one — each round only became visible after saving and watching the app break. Submitting the form now probes `?action=version` on the pasted URL first (token-less, so it costs nothing): an exact version match saves and reloads immediately; anything else — older version, no `version` action at all, or a 20s timeout for a cold start — explains what was found and offers an explicit "Lưu địa chỉ này" button rather than silently committing to it. There's also a guard for a `/dev` URL, which is the Apps Script test endpoint and never works for this. Every deployment of one script project shares the same bound Sheet and Script Properties, so switching URLs never splits or loses data — worth remembering before "fixing" a duplicate-deployment situation by rebuilding anything.
- **Connect-by-link, and a delegated-selector bug it exposed.** The connection can now arrive in the URL fragment (`#url=…&token=…`): a link with both connects the device outright, a link with only the URL just pre-fills the field, and the hash is stripped via `history.replaceState` the moment it is read. The **fragment** is deliberate over a query string — browsers never transmit it, so GitHub Pages and its logs never see the token. Settings gained "Mở sổ trên thiết bị khác", which builds that link from the config already in the browser (the token never leaves the device except into a link the user moves themselves) and says plainly that the link is a password. **Adding these surfaced a latent bug in the previous commit**: new button ids were appended to the click-handler's `switch` but never added to the `closest(...)` selector, so `#save-connection-anyway` had shipped completely dead — it rendered, and clicking it did nothing. It was missed because that button was only ever verified as *appearing*, never clicked. There is now a two-way audit (every id in the selector has a case, every case has an id in the selector); run it after touching either. **Verify a delegated button by clicking it, not by asserting it rendered.**
- **v3.6 fixed the worst bug in the project's history, and it was invisible to every test that existed.** On a real Google Sheet, a cell written as the string `"2026-08-02 12:00:00"` is coerced into a date VALUE, so `getValues()` hands back a **JS `Date`, never the string that was written**. `String(date)` then yields `"Sat Aug 02 2026 …"`, `parseDateOnly_` produces `NaN`, and every period id becomes `"NaN-NaN"` — essential spend read as `null`, current-period spend as `0`, runway/health/budgets/forecast/events all silently dead. The app looked fine; it just quietly reported nothing. **The Node suite never caught it because the in-memory fake returns whatever was appended — strings.** Fixed with `normaliseCell_` at the single read choke point (`sheetRowsAsObjects_`), which converts any Date back to `yyyy-MM-dd HH:mm:ss` in the spreadsheet's timezone, plus `toPeriodId_` for the `period_id` comparisons (Sheets coerces `"2026-07"` too). Detection uses `Object.prototype.toString.call(v) === "[object Date]"`, **not `instanceof Date`** — instanceof fails across realms, which is exactly how this first appeared fixed in a test while staying broken. Four regression tests now feed real `Date` objects through bootstrap, budgets and recurring. **Any future fake Sheet must return Dates for date columns, or it is not testing the real thing.**
- **Amounts are grouped as you type and spelled out everywhere.** One delegated handler formats every `input[inputmode="numeric"]` (`App.formatAmountInput`), so `10000000` reads back as `10.000.000` and can't be mistaken for a million; it bails the instant a letter appears so the `1tr` shorthand still survives, and restores the caret by counting *digits* rather than characters. Display-side, `formatCompact` no longer renders any money — every figure is written in full per the user's brief ("hạn chế viết tắt"). That made long numbers a layout risk, so the CSS gained real overflow guards (`min-width: 0` on flex children, `overflow-x: clip` on the root, a 22.5rem breakpoint); verified programmatically at 320px across all 11 screens with zero offenders.
- **Dialogs are dismissable three ways** (✕ button, backdrop click, Escape) — previously only a text "Đóng" existed and the user reported the close affordance as unusable. Switching a Kế hoạch sub-section no longer scrolls the page back to the top: `switchTab` only jumps when the tab actually changes, and the chosen chip is scrolled into view instead.
- **Screenshot import takes a batch.** The file input is `multiple`; images are processed **serially** (Apps Script cold-starts badly under a burst, and serial is what makes per-image progress and per-image failure reporting possible), candidates accumulate across images and are de-duplicated across them by `external_ref` too — the same receipt shot twice, or a list view plus its detail view, is a real habit. Verified with 12 images in one go. A dashboard "Tiền đi đâu kỳ này" card renders `metrics.concentration.breakdown` (already computed since v3, never displayed) as a proportion bar plus exact figures.

## Architecture

**Storage**: single SQLite file at `data/finance.db`, gitignored (per docs/THIET-KE.md, real financial data must never be committed). Every module resolves the project root as `Path(__file__).parent.parent` and connects with `PRAGMA foreign_keys = ON` and `row_factory = sqlite3.Row`.

**Schema** ([src/schema.sql](src/schema.sql)), defined and explained in full in docs/THIET-KE.md Part 3:
- `accounts` — one row per money store (bank, ewallet, credit_card, cash, savings). `is_liquid` flags whether it counts toward liquidity/emergency-fund calculations (e.g. credit card debt is not liquid).
- `categories` — self-referencing tree via `parent_id`. `kind` is expense/income/transfer — **`transfer` finally has a real writer as of 2026-07-29** (`transaction.insert_transfer`, see "Account transfers" below); before that it was seeded since Stage 1 but never actually used by any CLI/web screen. `necessity` (essential/optional) powers the risk metrics in `risk.py` (50/30/20 rule, "months of runway" if income stops — see below). `stability` (fixed/variable) is read by `risk.suggest_period_budget_amounts` (Mốc 1) and `risk.get_financial_rigidity` (Mốc 5) — this bullet used to say it was still unread by anything, which stopped being true as of those two and was simply never corrected here until now.
- `transactions` — the central table. `amount` is always positive; sign is carried separately in `direction` (in/out). `source` is `manual`/`recurring`/`ocr` in practice today (`email` is in the schema's CHECK constraint but has no writer — Stage 3 was skipped, see overview). `is_reviewed` exists for a not-yet-built *batch* review workflow; both `recurring`- and `ocr`-sourced transactions are still inserted with `is_reviewed = 0` (manual entries are `1`), but as of Mốc 5, `update_transaction_category()` also flips it to `1` — editing a transaction's category (CLI menu 8, web's edit page) now counts as the human review this column was meant to track, and logs a `transaction_reviewed` behavior event alongside the pre-existing `category_overridden` one. That's still not the same thing as the design doc's dedicated batch "chờ duyệt" screen, which doesn't exist — this only marks a row reviewed when its category happens to get touched, not on a schedule or in bulk. `external_ref` is the dedupe key; OCR import is its first real user (see below).
- `behavior_events` — structure existed unwritten-to since Stage 1 by deliberate design (see THIET-KE.md Part 5: "tạo cấu trúc từ Giai đoạn 1, chỉ ghi dữ liệu thật từ Giai đoạn 2"). As of Mốc 5, every event type THIET-KE.md envisioned finally has a writer: `category_overridden` (`log_behavior_event`, when a transaction's category is edited), `transaction_reviewed` (same edit — see below), `alert_shown` (`alerts.log_shown_alerts`, when a risk warning is displayed), `alert_acted_on` (`/alerts/<code>/dismiss`, when the user dismisses one from the dashboard), `event_plan_created` (inside `transaction.create_event_plan()`), and two the user asked to add beyond THIET-KE.md's own list — `ai_suggestion_accepted`/`ai_suggestion_rejected` (`web_app.py`'s `import_confirm()`, comparing the category the user actually submitted against Gemini's `suggested_category_id` for that row). Don't add a writer for a hypothetical future event type before the feature that produces it actually exists — that's still the operating principle, it's just that every type on the books today has one now.
- `rules` — auto-categorization: `pattern` is matched case-insensitively as a substring of a transaction's `description`; on match, `category_id` is assigned and `hit_count` increments. Tried highest-`priority` first. `created_from` distinguishes rules added directly (`'user'`, via CLI menu option 4) from ones learned by correcting a transaction's category (`'learned'`, via CLI menu option 8 or the web's edit-transaction page).
- `recurring` — recurring transaction templates (rent, subscriptions, ...). `next_due` advances by `frequency` (monthly/quarterly/yearly) each time it fires; `day_of_period` is stored but not currently used to compute due dates (next_due is set explicitly and advanced from itself, not recalculated from day_of_period — don't assume it's authoritative). Added via CLI menu option 6 only.
- `income_sources` — THIET-KE.md 3.7: each row is one income stream (a teaching job, a scholarship, freelance work, ...) with an `expected_amount` and a `reliability` (0–100%). The point of keeping this separate from `transactions` income history is right there in the design doc: a side gig's *expected* amount shouldn't be treated as certain just because it's expected — `reliability` is what lets `risk.py` discount it. Added via CLI menu option 10 only.
- `budgets` — **not in THIET-KE.md**, added by request inspired by Timo's "Hũ chi tiêu" (envelope budgeting per-category — THIET-KE.md 7.3 itself notes this general method as "chưa triển khai" at design time). One row per category with an active `monthly_limit`; `set_budget()` upserts (one active budget per category — setting it again replaces the limit, it doesn't insert a confusing duplicate row).
- `event_templates` / `event_items` (THIET-KE.md 3.8): a template (Chuyển nhà, Cưới hỏi, Du lịch — seeded in `seed_data.py`'s `_seed_event_templates`, guarded by its own count check so it seeds independently even on a re-run where categories already exist) with suggested line items. **Item *names* only, never a suggested price** — that's the design doc's explicit principle (price depends on locale/circumstances, guessing it would be wrong and erode trust), strictly followed when picking Cưới hỏi/Du lịch's item lists too (well-known checklist items, not financial advice).
- `event_plans` / `event_plan_items` — a real plan the user builds, optionally from a template (`template_id` nullable — a plan can be fully custom). `event_plan_items` is **not explicitly named in THIET-KE.md** but is a necessary, directly-justified extension of it: the doc says `event_plans` should carry "expected vs. actual" amounts, and that only makes sense tracked per line item. `expected_amount` is user-entered per item when creating the plan (CLI menu 15, `create_event_plan_interactive`); `actual_amount` exists in the schema for the same reason but **has no CLI/web writer yet** — don't assume it's populated anywhere.
- Tables described in the design doc but still **not in schema.sql**: `income_sources`' sibling concept from Part 7 (theory background, not a table) and anything from later stages (email/OCR-adjacent). When implementing a later stage, add tables incrementally rather than scaffolding them all up front.

**Migrations** ([src/migrations/](src/migrations/) + [src/migrate.py](src/migrate.py), added 2026-07-26 for the "hoạch định tương lai" expansion): `schema.sql`'s `CREATE TABLE IF NOT EXISTS` pattern stays as the original, once-only schema and is **never edited retroactively** — every table added since is a numbered file (`001_ai_infra.sql`, `002_period_settings.sql`, `003_period_budgets.sql`, `004_goals.sql`, `005_simulations.sql`, `006_cashflow_forecast.sql`, `007_investment_stub.sql`), each purely additive (`CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ... ADD COLUMN`, never `DROP`). `migrate.py` tracks which filenames have already run in a `schema_migrations` table, which exists specifically because SQLite has no `ADD COLUMN IF NOT EXISTS` — re-running the same `ALTER TABLE` twice raises `duplicate column name`, so unlike `schema.sql`, a migration file is *not* naturally safe to execute more than once on its own; the tracking table is what makes `migrate.py` itself safe to re-run. Current tables added this way (none are in `schema.sql`, none in docs/THIET-KE.md's original Part 3):
  - `ai_cache` / `ai_calls` (`001_ai_infra.sql`) — see `services/ai_client.py` below.
  - `app_settings` (`002_period_settings.sql`) — generic key-value config; today holds exactly one key, `period_start_day` (default `'15'`), read/written through `period.py`, never queried directly elsewhere. A settings table rather than an env var specifically because the user wants to reconfigure the period's start day at runtime, which an env var can't do without a restart.
  - `period_budgets` (`003_period_budgets.sql`) — supersedes `budgets`/`get_budget_status` (still in `schema.sql`/`risk.py`, deliberately untouched — see below) for anything period-aware. One row per `(category_id, period_id)` — `period_id` is a `period.py` id (see below), not a calendar month — with an `amount` and a `source` (`manual` / `suggested_fixed` / `suggested_variable` / `ai_adjusted`) recording *how* that number got there.
  - `goals` (`004_goals.sql`, Mốc 2) — see "Financial goals" below. Same migration also `ALTER TABLE event_plans ADD COLUMN`s three new columns onto the pre-existing `event_plans` table (`event_date`, `linked_goal_id`, `goal_prompt_dismissed`) — `event_plans` had **no date field at all** until this migration; found missing while designing the goals↔event-plan link and added because the link structurally needs it, not speculative scaffolding.
  - `spending_simulations` / `spending_simulation_scenarios` (`005_simulations.sql`, Mốc 3) — see "Spending-decision simulation" below. `spending_simulations.baseline_balances` and `.ai_recommendation` are both **frozen at creation/first-AI-call time**, never recomputed on a later page view — the whole point of saving a simulation is to look back later and see what was actually projected/recommended *then*, not a number that's silently drifted since.
  - `cashflow_forecasts` / `cashflow_forecast_periods` (`006_cashflow_forecast.sql`, Mốc 4) — see "Cashflow forecasting" below. `scenario` distinguishes `'base'` from `'macro_adjusted'`; a macro-adjusted row's `base_forecast_id` points back at the base it was derived from, and its own `macro_adjustment`/`macro_context_note`/`macro_context_sources` are a durable copy of what was actually shown/applied at the time — same "freeze it, don't recompute later" reasoning as the simulation tables above.
  - `investment_assets` (`007_investment_stub.sql`, Stage 7 prep, added alongside Mốc 5) — schema-only placeholder: `name`/`asset_type` (stock/fund/gold/crypto/fx/other)/`quantity`/`unit_cost`/`current_value`/`is_active`. Its **only** reader anywhere in the app is `risk.get_total_net_worth()`'s `SUM(current_value)` (see "Health-score dashboard" below) — no CLI/web screen creates or edits a row, so it stays at 0 rows until Stage 7 itself is actually built. **Don't build Stage 7 logic just because the table exists.**

**Financial periods** ([src/period.py](src/period.py), added 2026-07-26): a "kỳ" (period) is a configurable cycle — default the 15th of one month through the 14th of the next (`app_settings.period_start_day`) — that replaced the calendar month for every period-shaped calculation in the app, per the user's explicit instruction that this must apply everywhere, not just new features. Pure date-math functions (`period_bounds(d, start_day)`, `period_id_for`, `period_bounds_for_id`, `shift_period_id`, `recent_period_ids_for`, `days_elapsed_and_remaining_for`) take `start_day` directly and have no DB dependency, specifically so they're unit-testable without a cursor (see `tests/test_period.py` — 18 cases, the **first test suite in this project**, covering boundary dates, year rollover, and start-day clamping in short months); each has a cursor-based convenience wrapper (`get_period_start_day`, `current_period_id`, `recent_period_ids`, `days_elapsed_and_remaining`) that reads the configured start day and delegates. A `period_id` is formatted like a calendar month (`"YYYY-MM"`, the period's start date) so it sorts the same way old month strings did, **but it is not a calendar month** once `period_start_day != 1` — don't compare a `period_id` against `strftime('%Y-%m', ...)` output as if they were interchangeable. `period.py` deliberately has zero dependency on `transaction.py`/`risk.py` (it's a leaf both of those import) — its own tiny `_add_months` duplicates `transaction.py`'s day-clamping helper on purpose rather than importing it, to avoid a circular import.

**Financial goals** ([src/transaction.py](src/transaction.py)'s `goals` CRUD + [src/risk.py](src/risk.py)'s `get_goal_progress`/`suggest_emergency_fund_target`, added 2026-07-26 as Mốc 2): a `goal` (`get_goals`/`get_goal_by_id`) is a long-running accumulation target — name, `goal_type` (`emergency_fund`/`savings`/`investment`/`medical`/`custom`, labeled via `web_app.py`'s `GOAL_TYPE_LABELS`), `target_amount`, `deadline`, and a required `account_id`. **Progress is read live from that account's `current_balance`, not a separately-tracked running total** — a deliberate simplicity trade-off: if two goals point at the same account, each independently shows that account's full balance (no automatic splitting of one pool across goals). This was weighed against adding a `current_amount` column that `insert_transaction`/`delete_transaction` would need to keep in sync, and rejected specifically to avoid a second source of truth that could drift from the account's real balance.
- `risk.get_goal_progress(cursor, goal, as_of=None)`: `progress_pct` (capped at 100), `remaining_amount`, `periods_remaining` and `required_per_period` (both via `period.periods_between`, inclusive of the current and deadline periods), and an `is_off_track` flag — **a simple LINEAR schedule comparison** (expected % = periods elapsed since the goal's `created_at` ÷ total periods to deadline), explicitly **not** a real forecast; Mốc 4's cashflow forecast is the intended home for anything more sophisticated than "are you roughly on a straight-line pace." `is_overdue` (deadline passed, target not yet met) takes precedence over `is_off_track` so a goal is never flagged both ways at once.
- `risk.suggest_emergency_fund_target(cursor)`: the `emergency_fund` goal type's own built-in suggestion — 6× `get_average_period_essential_expense()`, the upper end of THIET-KE.md 7.3's "quỹ khẩn cấp 3–6 tháng" band (same source `runway_months`' reference bands already use). Returns `None` under the same has-data convention as the function it wraps; `/goals/new`'s JS only auto-fills the target field from this suggestion when the user hasn't already typed one.
- **`event_plans` ↔ `goals` linkage, per the user's own proposed division of labor**: `event_plans` = a specific, usually 1–2-period event (a trip, a birthday); `goals` = a multi-period accumulation target. `web_app.py`'s `events_new()` fires a **one-time** prompt — never a recurring nag — right after creating an event plan, when `SUM(event_plan_items.expected_amount) >= 10,000,000đ` **and** the event is `>= 2` periods away (via `period.periods_between`); the created plan redirects to `/events/<id>?suggest_goal=1`, which shows the prompt only if `linked_goal_id` is still null **and** `goal_prompt_dismissed` is still 0. Accepting pre-fills `/goals/new` via query params (name/target/deadline **and now, since 2026-07-29, `event_plan_id`** from the event); declining calls `dismiss_event_plan_goal_prompt()`, which sets the flag permanently — the prompt never resurfaces for that plan either way once acted on. **`transaction.link_event_plan_to_goal` was found never actually called anywhere while auditing on 2026-07-29** (a real bug dating back to Mốc 2 itself, not something the hardening pass introduced) — the "Tạo mục tiêu" link only ever pre-filled `/goals/new`'s fields via query params, it never passed `event_plan_id` through or called this function, so `linked_goal_id` never actually got set and the same prompt would silently reappear on every later visit to that event even after the user "accepted" it once. Fixed: the link now also carries `event_plan_id`, `goals_new()`'s form carries it forward as a hidden field, and its POST handler calls `link_event_plan_to_goal()` after creating the goal, when present.
- **`transaction.deactivate_goal` had the same problem, also since Mốc 2**: defined, but no CLI menu option or web route ever called it, so a goal — once created — had no way to ever be marked done or abandoned; `get_goals()` only ever lists `is_active = 1` rows, so a completed goal would just sit in the list forever with no way to remove it short of editing `data/finance.db` directly. Fixed 2026-07-29: `POST /goals/<id>/deactivate` (first caller), a plain button on `/goals/<id>` ("Ẩn mục tiêu này") with a `confirm()` guard — same UX pattern as `/rules`'/`/transactions`' own delete buttons. Deliberately named/framed as "ẩn" (hide), not "xóa" (delete) — `is_active = 0` keeps the row (and its history) intact, it just stops showing up in `get_goals()`, `_goals_status_summary()` (the dashboard card), and `_total_goal_contribution_per_period()` (the forecast/budgets integrations) alike, all for free since they all already filter on `is_active`.
- **`/events` + `/events/new` is a new web equivalent for what was previously CLI-only** (menu 14–16) — added specifically so the event↔goal linkage above is reachable at all from the phone browser, the app's primary surface; without it, creating an `event_plan` (the trigger for the whole feature) would have stayed impossible from the web. `events_new()`'s form supports picking one of the seeded `event_templates` (pre-fills its `event_items` as read-only name fields with a blank amount input each, exactly like the CLI's own "chỉ gợi ý khoản mục, giá tự nhập" flow) plus a handful of blank custom-item rows, submitted together in one POST.
- Multi-goal AI prioritization (`/api/ai/goal-priority`, only surfaced on `/goals` when `len(goals) >= 2`) sends each goal's already-computed `remaining_amount`/`periods_remaining`/`required_per_period` and asks the AI to rank them and explain why, citing common personal-finance heuristics (emergency fund before investment, high-interest debt before savings) only where relevant — never computing new numbers itself, same standing rule as every other `ai_client` call.

**Spending-decision simulation** ([src/risk.py](src/risk.py)'s `compute_spending_scenarios`/`project_simple_trajectory`/`get_baseline_period_flow`/`traffic_light_for_trajectory` + [src/transaction.py](src/transaction.py)'s `spending_simulations` CRUD, added 2026-07-26 as Mốc 3): "before you buy something big, see the impact first."
- `project_simple_trajectory(cursor, periods_ahead, extra_expenses=None)`: projects liquid balance forward by continuing the recent average income/expense flat (`get_baseline_period_flow`, itself just reusing `get_savings_rate_trend`'s own data rather than re-querying). **Deliberately simple, not a real forecast** — no seasonality, no goals, no budgets layered in. This exists purely to power Mốc 3's "with vs. without this expense" chart; **Mốc 4's cashflow forecast is a separate, richer model and should not just extend this function in place** — check whether Mốc 4's own forecast already supersedes this before touching it.
- `compute_spending_scenarios(cursor, *, item_amount, maintenance_cost_per_period=0, expected_lifetime_periods=0)`: builds all 6 comparison scenarios in one call — pay now, installments over `INSTALLMENT_OPTIONS` (3/6/12 periods), delay by `DELAY_OPTIONS` (3/6 periods) — plus the no-expense baseline. `total_cost_of_ownership` (`item_amount + maintenance × lifetime`) is **identical across every scenario** — no financing/interest cost is modeled, since none was asked for and an invented interest rate would be a number this app has no basis to assume; only the *timing* of the cash outflow differs between scenarios. Every number here is plain Python arithmetic — no AI involved anywhere in this function.
- `traffic_light_for_trajectory`: green/yellow/red, reusing the *same* essential-period-expense threshold `liquidity_risk` already uses for "sufficient" (not a new, separately-invented threshold) — red if any projected period goes negative, yellow if it dips below that threshold without going negative, green otherwise; falls back to a plain negative/non-negative check (no yellow tier) when there's no essential-spend history yet to know the threshold from.
- **The AI's role is explanation only, and it never sees raw numbers it could second-guess into a new one** — `/api/ai/simulation-advice` sends each scenario's already-computed `total_cost_of_ownership`/`traffic_light`/`projected_balances` and asks for 1 sentence of pros + 1 of cons per scenario, plus one clear recommendation with reasoning — never asked to compute anything. Runs on `GEMINI_MODEL_HEAVY` (not the default flash-tier model) per the user's own request that Mốc 3/4 use the heavier model for analysis — **this is the first real usage of `GEMINI_MODEL_HEAVY`/`gemini-pro-latest`, unconfirmed against a real key as of this writing** (see `services/ai_client.py`'s own note about needing a live smoke test).
- **The recommendation freezes permanently on first success**: `/api/ai/simulation-advice` checks `spending_simulations.ai_recommendation` first — if already set, returns it directly with no API call at all; only calls `get_ai_suggestion` (and then writes the result back via `set_simulation_ai_recommendation`) the first time. This is stronger than `ai_client`'s own TTL-based cache (which would still exist underneath, keyed on `task="simulation_advice"`, but is effectively moot here since the frozen column is always checked first) — deliberately so, because the whole point of saving a simulation is to compare a past recommendation against what actually happened later, which a refreshable cache would undermine.
- **Triggered contextually from the add-transaction form (Mốc 3's own requirement; that form was still `/` at the time — it's `/add` since Mốc 5, see "Health-score dashboard" below)**: `PAGE_TEMPLATE`'s add-transaction JS intercepts `POST /api/transactions` submissions where `direction === "out"` and `amount >= 1,000,000` with a native `confirm()` ("bạn có muốn mô phỏng trước khi lưu không?"); accepting navigates to `/simulate?amount=...&name=...` **without saving the transaction** — the user simulates first, then (if they still want to) goes back and logs the real transaction separately. This is a functional addition to that form's own JS, not a visual redesign, so it doesn't conflict with `PAGE_TEMPLATE` otherwise staying on the old `BASE_STYLE` system.
- **First use of a JS charting library in this project** (`SIMULATION_DETAIL_TEMPLATE` only, not global): Chart.js loaded from `https://cdn.jsdelivr.net/npm/chart.js@4`, **pinned to a major version** unlike Tailwind's floating CDN tag — Chart.js's API has real breaking changes across major versions, and this project already has a concrete lesson (`gemini-2.5-flash`'s alias-vs-pinned-name incident) about what an unpinned identifier changing underneath the app looks like. The chart itself shows exactly 2 lines (baseline vs. pay-now-with-the-expense), not all 6 scenarios overlaid — the rich multi-scenario comparison lives in the table below it instead, matching the spec's own "số liệu trước, khuyến nghị sau" (numbers first, then verdict) ordering and keeping the chart itself readable.

**Cashflow forecasting** ([src/risk.py](src/risk.py)'s `compute_cashflow_forecast`/`project_recurring_by_period`/`detect_seasonality` + [src/transaction.py](src/transaction.py)'s `cashflow_forecasts` CRUD, added 2026-07-26 as Mốc 4): projects liquid balance 6–12 periods ahead, chaining each period's ending balance into the next one's start (the "rollover" the user asked for — `accounts.current_balance` itself never needed any new rollover logic, since it's already a continuously-running total; this chaining is purely internal to the forecast loop).
- **Inputs, combined without double-counting**: `project_recurring_by_period(cursor, period_ids)` simulates each active `recurring` item's *own* occurrences forward from its real `next_due`/`frequency` (a quarterly item does not appear in every period — verified in `tests/test_risk.py`), giving real per-period recurring in/out. `get_reliable_monthly_income()` (already built for Mốc 2's `income_sustainability_margin`) is applied every period as the "chắc chắn" income floor. The user's own manual per-period estimates for uncertain income (`irregular_income_by_offset`, a `{period_offset: amount}` dict) cover THIET-KE.md 3.7's "thu nhập thất thường" case. **"Ngân sách đã lập" (`period_budgets`) is deliberately NOT folded into the forecast number itself** — a budgeted category can also be a recurring item, and reconciling that overlap correctly (without either double-counting or silently dropping spend) was judged too real a correctness risk for the time available; instead "other variable spend" uses the same historical-average approach as Mốc 3's `project_simple_trajectory` (recent average total expense minus recent average recurring expense). If a future pass wants budgets to feed the number directly, that reconciliation still needs solving, not just wiring the columns together.
- **Goals feed in as a genuinely new outflow, not a double-count**: the caller (web_app.py's `_total_goal_contribution_per_period`) sums every non-overdue active goal's `required_per_period` (from `get_goal_progress`, Mốc 2) and passes the total in as `goal_contribution_per_period` — applied as a flat amount every period in the forecast window. **Known simplification, documented not silently assumed**: a goal's contribution keeps applying even past that goal's own deadline within the forecast window, since properly stopping it at the right offset would need per-goal period-by-period bookkeeping this function doesn't do.
- **Seasonality detection is descriptive statistics only, and never applies itself**: `detect_seasonality(cursor)` computes mean/stdev total 'out' spend per calendar-month-position across every *completed* period of history, comparing each month's average against the overall average; a month only becomes a "pattern" if it's been observed ≥2 times and differs from the overall average by ≥`SEASONALITY_PCT_THRESHOLD` (15%), and only runs at all once ≥`SEASONALITY_MIN_PERIODS` (12) periods of history exist (need at least one full annual cycle to say anything). Both thresholds are fixed Python constants — **the AI is never involved in detection or in deciding the threshold**, only (nowhere yet built, but reserved as a future touchpoint) in describing a detected pattern in plain language, per the user's explicit "AI diễn giải căn cứ đó, nhưng ngưỡng tin cậy do công thức quyết định." A detected pattern only ever affects a forecast when the user explicitly ticks "Áp dụng quy luật mùa vụ" on `/forecast`'s generate form — `compute_cashflow_forecast`'s `seasonality_patterns` parameter is the only way it reaches the calculation, and nothing populates it automatically.
- **The macro-context layer is real but genuinely separate and low-confidence**: `services/ai_client.py`'s `get_macro_context(cursor, prompt)` is a **dedicated function, not `get_ai_suggestion`** — Gemini's Google Search grounding tool (`types.Tool(google_search=types.GoogleSearch())`) doesn't reliably combine with forced structured JSON output, so this call requests plain text and parses `response.candidates[0].grounding_metadata.grounding_chunks[].web.{title,uri}` for sources — **this exact parsing shape is UNCONFIRMED against a real API response as of this writing**, flagged the same way the OCR model-alias lesson is elsewhere in this doc; verify live before trusting it, don't assume it just works. Gated off by default (`ENABLE_MACRO_CONTEXT` env var, unset/anything-but-`"1"` = disabled) and, even when enabled, only ever fetched by an explicit button click on `/forecast` (`/api/ai/macro-context`), never auto-loaded — the single most expensive/slowest/least deterministic AI feature in the app, deliberately shipped last and opt-in only, per the plan's own risk callout. Its output is shown in a visually separate card, explicitly labeled as general market information, not personal financial advice, and **never mixes into the forecast numbers automatically**: applying it requires the user to type their own adjustment amount (a real number they choose, informed by but not computed by the AI) into a small form, which creates a brand-new `scenario='macro_adjusted'` forecast (`/forecast/<id>/macro-scenario`) sitting *alongside* the original base forecast (linked via `base_forecast_id`), never overwriting it.
- Exposed via `/forecast` (shows the latest base forecast + the generate-new form + seasonality suggestion box + the gated macro-context section) and `/forecast/<id>` (any specific forecast, base or macro-adjusted, by id — also how a macro-adjusted scenario and its base are cross-linked for side-by-side comparison).

**Health-score dashboard** ([src/risk.py](src/risk.py)'s "Health-score dashboard (Mốc 5)" section + `web_app.py`'s `dashboard()`/`add_transaction_page()`, added 2026-07-26 as Mốc 5, the final milestone of the "hoạch định tương lai" plan): **`/` is no longer the add-transaction form** — that form is now `add_transaction_page()` at `/add` (same `PAGE_TEMPLATE`, unchanged except its alert banner was removed — see below). `/` is now `dashboard()`, a brand-new Tailwind-based page (unlike `/risk`/`/import`, which stayed on `BASE_STYLE` — this is genuinely new, not a legacy carryover, so it follows every other post-redesign page onto Tailwind) built around one composite health score.
- `risk.get_health_score(cursor, as_of=None)` is the headline number: starts from `runway_months()`'s level (`nguy_hiem`/`mong_manh`/`on`/`vung` — reused verbatim as `HEALTH_LEVELS`, the app's most stable, longest-horizon signal) and only ever **downgrades**, never upgrades, by up to one level each for two more urgent signals: `short_term_forecast().at_risk` (an immediate this-period cash-out risk that a multi-period runway number wouldn't otherwise surface) and `get_burn_rate_vs_elapsed().ratio > BURN_RATE_DANGER_RATIO` (1.5× — spending faster than the period's elapsed-time pace). **Never upgrading past what `runway_months` itself says is deliberate** — THIET-KE.md 7.2's Loss-Aversion framing again: when signals disagree, this app errs toward the more cautious one, not the more optimistic one. Returns `{"level", "has_data", "downgraded_reasons": [...]}` — `has_data=False` (same convention as `runway_months`) until there's at least one completed period of essential spending.
- Seven component metrics, all in `risk.py`, all accepting the same `as_of` override as every other function in the module for testability: **`get_survival_days`** (liquid balance ÷ `get_average_daily_total_spend`, a NEW function distinct from the pre-existing `get_average_daily_variable_spend` — this one deliberately **includes** recurring-sourced spend, since "how many days can I survive" should count bills, not just discretionary spend the way `short_term_forecast`'s math does); **`get_financial_rigidity`** (fixed-category spend ÷ income over the last 3 completed periods — the **first real read of `categories.stability`** for anything beyond Mốc 1's budget-suggestion formula, closing out a column that had sat designed-in-but-unread since Stage 1); **`get_burn_rate_vs_elapsed`** (% of this period's `period_budgets` spent vs. % of the period elapsed — `has_data=False` if nothing's budgeted this period yet); **`get_current_period_savings_rate`** ((income−expense)/income for just the elapsed part of the current period — a "how's today going" complement to `get_savings_rate_trend`'s completed-periods-only view); and three the user explicitly delegated the choice of ("tôi giao anh toàn quyền chọn"): **`get_spending_concentration`** (which top-level category — children rolled up to their parent via `COALESCE(parent_id, id)` — is eating the largest % of this period's spend so far), **`get_income_stability`** (coefficient of variation — stdev÷mean, as a %— of income across the last 6 completed periods; reuses `get_savings_rate_trend`'s own period data rather than re-querying), and **`get_budget_streak`** (consecutive completed periods, most-recent-first, with no `period_budgets` category over its limit — stops counting at the first over-budget period or the first period with no budgets set at all, whichever comes first).
- **`get_total_net_worth(cursor)`**: sum of every active account's `current_balance` (**not** filtered to `is_liquid` — a deliberate difference from `get_liquid_balance`, which answers "usable right now" rather than "total owned") plus `SUM(investment_assets.current_value)` (0 today, see the migrations bullet above). **Explicitly documented in its own docstring never to be used by any safety calculation** (`liquidity_risk`, `runway_months`, `short_term_forecast`) — mixing in illiquid assets would make those numbers look safer than they really are, exactly the wrong direction of error for a safety metric.
- **Proactive envelope-budget reminders** (a second, more granular layer than `alerts.py`'s whole-account warnings — THIET-KE.md 1.3's "Phòng ngừa" pillar applied at the category level this time): `dashboard()` pulls this period's `risk.get_period_budget_status()`, sorts by `pct_used` descending, and shows the top 3 as either "Còn X đ cho [danh mục] trong Y ngày còn lại của kỳ" (on track) or "Đã vượt ngân sách [danh mục]: ..." (already over) — computed fresh on every page load, not a stored/dismissible state.
- **`alerts.get_active_alerts()`'s banners moved from `/add` to `/`** — this dashboard is now the real "moment the app opens" per CLAUDE.md's own already-stated principle for that feature, so `add_transaction_page()` no longer fetches or shows them (its old alert-banner CSS was removed from `PAGE_TEMPLATE` as dead code along with it). Each banner now has an "Đã xem" button (`POST /alerts/<code>/dismiss`) that logs an `alert_acted_on` behavior event — **purely an analytics write, not a suppression mechanism**: there's no "dismissed" column anywhere, so a still-true condition reappears on the next load. That's intentional, not a bug — the app has no schema for muting future occurrences of a real, ongoing risk, and inventing one wasn't part of this milestone's ask.
- **AI daily summary** (`/api/ai/daily-summary`, `DailySummaryResult` Pydantic model, `prompts/daily_summary.md`): 2–3 sentences summarizing the health score, net worth, and component metrics for today, using the exact same `get_ai_suggestion` caching contract as every other AI feature — the **"once per day" requirement falls out for free** by folding `date.today().isoformat()` into `input_data`, so the cache key (and thus a real API call) only changes once a day, with `ttl_seconds=24h` as a backstop rather than the actual mechanism. Auto-fetched via a plain `fetch()` in `DASHBOARD_TEMPLATE`'s own `<script>` (same "load client-side after the page's own numbers already rendered" pattern as `/budgets`' AI panel, not click-gated the way the much more expensive/slower macro-context feature is) into a panel that stays hidden if Gemini is unavailable — same graceful-degradation contract as everything else built on `get_ai_suggestion`. **Deepened 2026-07-29** (see "Cross-feature integration pass" below) to also see goals/events, not just risk.py's own metrics.

Built from `web_app.py`'s `_goals_status_summary(cursor)` and `_nearest_upcoming_event(cursor)` helpers, which `/api/ai/daily-summary` also calls (see below), so the dashboard card and the AI's synthesis always describe the same goal/event state, never two independently-computed answers.

See the "Two design systems" bullet below for the updated full link lists.

**Amount parsing and form-error UX** (`transaction.parse_amount_vnd`, added 2026-07-27 during the product-hardening pass): every money-amount text field in the web app used to parse input as `int(raw.replace(",", "").replace(".", ""))`, or on `/add` itself, reformat the field destructively on every keystroke (`amountInput.value = digits_only`). Confirmed live before fixing: typing the everyday Vietnamese shorthand **"1tr"** into `/add`'s amount field got silently stripped down to just **"1"** as the user typed — 1 đồng recorded instead of 1,000,000, no warning, no error, nothing — and on `goals_new`/`events_new`/`simulate_page`/`budgets_save`, a value that failed the naive parse didn't even save partially, it just silently vanished (the whole form redirected to itself with no query params, wiping everything the user had typed, in `goals_new`/`simulate_page`'s case; in `budgets_save`'s case, that ONE category's amount was skipped with zero indication which category or why).
- `parse_amount_vnd(raw)` is the one shared fix: plain digits with "," / "." as a thousands separator still work exactly as before, but now also understands "500k" (nghìn, ×1,000), "1tr"/"1.5tr"/"1,5tr"/"2trieu" (triệu, ×1,000,000), "2ty"/"2tỷ" (tỷ, ×1,000,000,000), and the colloquial "2tr5" pattern (a trailing digit right after "tr" means tenths of a million — 2tr5 == 2.5 triệu == 2,500,000, a real pattern in everyday Vietnamese chat/SMS). Raises `ValueError` with a Vietnamese message on anything else, rather than silently truncating or dropping the input — every caller is expected to show that message, not swallow it. 24 hand-written cases in `tests/test_transaction.py`'s `ParseAmountVndTests`.
- **`/add`'s amount field no longer destructively reformats while a shorthand unit is still being typed**: the `input` handler now pauses its live "1.234.567" reformatting the moment a letter appears in the field (so "1tr" survives being typed), and the field's raw text — not a pre-parsed integer — is what's actually sent to `POST /api/transactions`; `create_transaction()` is what now calls `parse_amount_vnd` server-side, the single source of truth for what gets saved. A client-side `tryParseAmount()` mirror still exists, but only for the ≥1,000,000đ simulate-prompt trigger and the empty-field pre-check — it's explicitly non-authoritative and never needs to be exact.
- **`goals_new`/`events_new`/`simulate_page`/`budgets_save` now redirect back to themselves with the typed values AND a Vietnamese error message preserved as query params** (`web_app.ERROR_BANNER`, a shared Jinja snippet reading a plain `error` query param — matching this app's existing "prefill via query params on redirect" idiom, not session-based Flask `flash()`) instead of silently wiping the form or silently skipping a field. `budgets_save` and `events_new`'s per-item-amount loop are still tolerant of a **blank** amount (an intentional "no estimate yet" per THIET-KE.md's own event-item design) but now surface a specific error listing which category/item failed to parse when a **non-blank** one does.
- **`/import/confirm` now reports what actually happened**: `saved`/`skipped_duplicate` counts existed since OCR import shipped but were silently discarded after the redirect; a new `skipped_invalid` count (amount failed `parse_amount_vnd`, or was ≤0, or had a bad direction) joins them, and `/transactions` now shows a one-time green banner ("Đã lưu N giao dịch từ ảnh, M trùng lặp đã bỏ qua, ...") built from `?import_saved=`/`?import_skipped_duplicate=`/`?import_skipped_invalid=` query params on the redirect.

**Account transfers** ([src/transaction.py](src/transaction.py)'s `insert_transfer`/`get_transfer_category_id` + [src/risk.py](src/risk.py)'s `NOT_TRANSFER_CLAUSE`, added 2026-07-29): `categories.kind` has allowed a `'transfer'` value since Stage 1's original schema, and `seed_data.py` has always seeded one ("Chuyển khoản nội bộ") — but **no CLI menu option and no web route ever actually used it**. That meant a genuinely common personal-finance action — topping up MoMo from a bank transfer, an ATM cash withdrawal, paying off a credit card from a bank account — had no correct way to be recorded: entering it as a plain expense/income transaction moves money between the user's OWN accounts while ALSO inflating their real income or expense totals, silently distorting every risk metric, savings rate, and budget status built on top of `direction`.
- `transaction.insert_transfer(cursor, *, from_account_id, to_account_id, amount, description, occurred_at=None)`: records the movement as two ordinary linked `insert_transaction()` calls (an 'out' leg from the source account, an 'in' leg to the destination, same `occurred_at`/`description`, both tagged with `get_transfer_category_id()`'s category) rather than inventing a new table or a third `direction` value. Raises `ValueError` if `from_account_id == to_account_id` or the transfer category is somehow missing. **Deliberately not linked at the DB level for cascade-delete** — editing/deleting one leg later doesn't automatically touch the other, a conscious scope limit (same risk that already exists if a user manually enters two related transactions today, not a new one).
- **`risk.NOT_TRANSFER_CLAUSE`**: every query anywhere in `risk.py`/`transaction.py` that sums `'in'`/`'out'` transactions **without already joining categories on something else** (necessity, parent rollup) had to be individually audited and fixed to exclude `categories.kind = 'transfer'` — otherwise a transfer would silently inflate income, expense, or "biggest spending category" by its amount. Fixed sites: `get_average_daily_variable_spend`, `budget_balance_50_30_20`'s income query, `get_savings_rate_trend`, `detect_seasonality`, `get_average_daily_total_spend`, `get_current_period_savings_rate`, `get_spending_concentration` (already joined categories — filters `c.kind != 'transfer'` directly instead), `get_financial_rigidity`'s income query, and `transaction.get_monthly_totals`. **Two queries needed no change**: `get_average_period_essential_expense`/`budget_balance_50_30_20`'s expense-by-necessity query already implicitly exclude transfers, since a transfer category's `necessity` is always `NULL` and nothing reads that bucket. `NOT_TRANSFER_CLAUSE` itself reads `(category_id IS NULL OR category_id NOT IN (SELECT id FROM categories WHERE kind = 'transfer'))` — the `IS NULL` half matters, since plain `NOT IN` would also wrongly exclude every **uncategorized** transaction (SQL's `NULL NOT IN (subquery)` evaluates to NULL/false, not true). Covered by `tests/test_risk.py`'s `TransferExclusionTests` (a large transfer alongside small real income/expense, confirming the transfer's amount never leaks into the result) and `tests/test_transaction.py`'s `InsertTransferTests`.
- **Web UI**: `/add`'s direction segmented control gained a third option, "Chuyển khoản" (blue, matching neither Chi/Thu's red/green), which swaps the category picker for a second "Đến tài khoản" account select and relabels the first as "Từ tài khoản"; submits to a new `POST /api/transactions/transfer` (mirrors `create_transaction`'s validation style: both accounts must exist and be active, `parse_amount_vnd` for the amount, a clear 400 JSON error on any failure) rather than `/api/transactions`. No CLI equivalent yet — add one only if asked, matching this app's existing "extend the web app only if asked" convention for CLI/web parity gaps.

Called by both `add_transaction()` (CLI) and `POST /api/transactions` (web) whenever the user leaves the category blank — never bypass this by inserting a transaction with a hardcoded category when the user didn't pick one.

**Risk metrics** ([src/risk.py](src/risk.py), a separate module from `transaction.py` — analytics is a distinct concern from transaction CRUD): implements THIET-KE.md Part 4, all read-only, no writes. **Retrofitted 2026-07-26 from calendar months to `period.py`'s financial periods** — the highest-regression-risk change of the whole "hoạch định tương lai" expansion, since this is code that was already shipped and already fed the home-page alert banner; see `tests/test_risk.py` (17 cases, hand-computed expected values, including a real before/after spot check against the actual `data/finance.db`) before touching any of these functions again:
- `short_term_forecast()` (4.1): projected available balance at period-end = liquid balance − recurring still due this period (`get_remaining_recurring_this_period`, only counts `next_due` strictly after today, since anything due today-or-earlier is assumed already turned into a real transaction by `generate_due_recurring`) − projected variable spend (`get_average_daily_variable_spend`, averaged over the trailing 30 days — a rolling day-count window, **not** period-based, and correctly untouched by the retrofit — **excluding `source = 'recurring'` rows** so recurring commitments aren't counted twice) × days left in the period.
- `liquidity_risk()` (4.2) and `runway_months()` (4.3) both build on `get_average_period_essential_expense()` — the average essential (`categories.necessity = 'essential'`) spend per financial period over the last 3 *completed* periods that actually have essential spending (a period with none is **skipped, not counted as 0** — same semantics the old calendar-month version had via SQL `GROUP BY`, preserved deliberately: a genuinely-empty period silently dragging the average down would understate a safety-critical number). Returns `None`/`has_data=False` until there's at least one completed period of essential spending — never silently show a runway/liquidity number computed from zero history.
- `budget_balance_50_30_20(cursor, period_id)` (4.4): essential/optional spend vs. income for one financial period (identified by a `period.py`-shaped `period_id`, not a calendar month), grouped via `categories.necessity`.
- `get_reliable_monthly_income()` / `income_sustainability_margin()` (THIET-KE.md 3.7, built alongside the `income_sources` table, not part of the original Part 4 quartet): weights each active income source's `expected_amount` by its `reliability`, then compares that "chắc chắn" (certain) total against `get_average_period_essential_expense()` — a different question from `runway_months()`, which only asks how long *existing savings* last with zero income; this asks whether *ongoing* reliable income already covers the essential baseline. `has_data` is `False` until both at least one income source and one completed period of essential spending exist. Kept named/shaped as a **monthly** figure on purpose — `income_sources.expected_amount` is a stated user input independent of the period cycle, not a transaction-derived aggregate, so there was nothing here to retrofit.
- `get_budget_status(cursor, month)` — **deliberately NOT retrofitted, still calendar-month, still reads the old `budgets` table** (see the `budgets`/`period_budgets` bullets above). Superseded by `get_period_budget_status(cursor, period_id)` (reads `period_budgets` instead) for anything new, but kept working exactly as before — orphaned, not migrated in place, so no data is lost and nothing breaks for whatever still calls it (CLI menu 12–13 only, as of Mốc 1).
- `get_savings_rate_trend(cursor, periods=6, as_of=None)` (not in THIET-KE.md, added 2026-07-26 by direct request to make the risk report more grounded in real personal-finance theory, retrofitted to periods the same day as part of Mốc 1): unlike every other metric here, which is a single point-in-time snapshot, this returns the savings rate — `(income − expense) / income` — for each of the last `periods` *completed* financial periods that have any transaction at all (same "skip periods with no data" convention as the essential-expense average above), oldest-first, plus a `trend` of `"improving"`/`"declining"`/`"stable"`/`None` comparing the oldest to the newest period with a defined rate. The rationale (see the function's own docstring) is that *rate*, not the absolute amount saved, is what personal-finance literature treats as predictive of trajectory — none of the other metrics show direction of change over time, only current standing. Returns `{"periods": [...], "trend": ...}` — the key is `periods`, not `months`, and each entry's key is `period_id`, not `month` (renamed as part of the retrofit; every caller was updated to match).
- `suggest_period_budget_amounts(cursor, period_id)` / `get_period_budget_status(cursor, period_id)` (Mốc 1's new period-budgeting feature, see `period_budgets` above): the former is formula-based budget suggestion (b) of the three ways to set a budget — `categories.stability = 'fixed'` copies the previous period's budget for that category verbatim if one exists (falls back to the `'variable'` rule if there's no previous budget to copy yet); `'variable'` averages *actual spend* in that category over the last 3 completed periods, **treating a zero-spend period as 0, not skipping it** — the opposite convention from the essential-expense average above, and deliberately so: for "how much do I typically spend here," an unused category genuinely should pull the suggestion down, whereas for a safety metric like liquidity, a missing data point pulling the number down in the wrong direction is the failure mode to avoid. Categories with no `stability` set, or whose computed suggestion is 0, are skipped (nothing useful to suggest). `get_actual_spend_in_period(cursor, category_id, period_id, start_day)` is the shared per-category-per-period spend query both of these (and `web_app.py`'s `/api/ai/budget-suggestion`) call — public (no leading underscore) specifically because it has three real callers, not one.
- All accept an `as_of` override (defaults to `date.today()`) specifically so they're deterministic to test.
- Exposed via CLI menu option 9 (`show_risk_report`) and the web's `/risk` page — both call the exact same `risk.py` functions and just format the same numbers differently; don't duplicate the math in either UI layer.

**Screenshot import via Gemini** ([src/ocr_import.py](src/ocr_import.py), web-only — see below for why): the user's workflow is to add a clear note to every MoMo/MB Bank transfer, then upload screenshots. **This used to be local Tesseract OCR + regex line-parsing** (see git history around 2026-07-24) — that approach was replaced after Tesseract kept misreading real screenshots in ways plain regex couldn't recover from: garbled/dropped labels, and a two-column layout sometimes read as "all labels, then all values" instead of label-value pairs in order, each needing a new, increasingly fragile heuristic (`_find_labeled_note`, `_find_note_before_footer`, `_find_ascii_lowercase_note`, `_clean_mb_noi_dung`, `_find_mb_content_value`, junk-character filters, ... — all deleted when this was replaced). A vision model reads the screen semantically instead of line-by-line, so it isn't tripped up by OCR reading order.
- **This is a real, deliberate trade-off, not a free upgrade**: the original Tesseract choice was made specifically so screenshots of real financial data never left the user's machine. Switching to Gemini means those photos are now sent to Google's API. The user made this trade-off explicitly after Tesseract's accuracy problems proved hard to fix with more regex patches (see memory `project_stage2_progress`) — don't revert it back to local-only OCR without the user raising it again, and don't casually add *other* cloud calls elsewhere in the app on the assumption this precedent makes it fine.
- `analyze_image(image_bytes, mime_type)` sends the image straight to the Gemini API (`google.genai`, model configurable via `GEMINI_MODEL` env var, defaults to `gemini-flash-latest`) with a prompt asking it to return structured JSON (`response_mime_type="application/json"`, `response_schema=` a Pydantic model) — one `{amount, direction, note}` object per real transaction found in the image. This replaces the *entire* old regex pipeline in one call; there is no separate "raw OCR text" step anymore, and no per-screen-shape special-casing to maintain — the prompt itself explains what a "note" is vs. a bank reference code, and asks the model to skip balance-only lines and to not double-count a restated amount.
  - `gemini-flash-latest` (an alias, not a dated model name) was picked deliberately over pinning e.g. `gemini-2.5-flash` — that pinned name actually failed at runtime with a real key ("no longer available to new users"), confirming Gemini model names churn fast enough that hardcoding a specific version is a real reliability risk. Confirmed working end-to-end (correct amount/direction/note) against several test images with a real API key on 2026-07-24. If this alias ever breaks, check `client.models.list()` for what's currently available rather than guessing a name from memory.
- Requires `GEMINI_API_KEY` in the environment — checked lazily (only when `analyze_image` is actually called), so the rest of the app works fine without it; only the `/import` page needs it. Get a free key at [aistudio.google.com/apikey](https://aistudio.google.com/apikey).

- `make_external_ref(amount, direction, note)` — since there's no bank reference number to key off, the dedupe key is a hash of `(amount, direction, note)`. Re-uploading the same screenshot produces the same hash, which collides with `transactions.external_ref`'s UNIQUE constraint; `web_app.py`'s `/import/confirm` catches `sqlite3.IntegrityError` per-row (committing after each successful insert, so one duplicate doesn't roll back the others in the same batch) and just skips that row. Unchanged from the Tesseract-era design.
- **Category is also AI-suggested, not just amount/direction/note**: `analyze_image` is given the full category tree (via `_format_categories`, built from `category_tree_as_json` for both kinds) as part of the prompt, and asked to return a `category_id` guessed from the *meaning* of the note (e.g. "tien gui xe" → a parking/transport category) — broader than `rules`' exact-substring matching. `analyze_image` validates any returned id against the real category set before trusting it (never take a model-generated foreign key on faith, even for a low-stakes field). In `web_app.py`'s `import_page()`, Gemini's guess wins; the existing `apply_matching_rule` (Stage 2's rules engine) is only consulted as a fallback when Gemini returns `null` (not confident enough to guess). Confirmed with a real API key across several notes — correctly distinguished categories like "Cà phê/Trà sữa" vs. "Ăn ngoài" vs. "Gửi xe" from note wording alone, and fell back sensibly (e.g. "Thu nhập khác") when no category was an exact fit.

Nothing extracted is ever written to the database without a human seeing it first — this safety property held under Tesseract and still holds under Gemini; don't remove it just because Gemini is more accurate.
- **Correcting the AI's category guess during review feeds the same "learn a rule" loop as correcting it after the fact** (2026-07-26, requested explicitly — the user didn't want the image-recognition categorization to stay "boxed in"/static as more screenshots come in): the review form (`IMPORT_REVIEW_TEMPLATE`) carries Gemini's original `suggested_category_id` per candidate in a hidden `suggested_{i}` field; in `import_confirm()`, if the category the user actually submits differs from that original suggestion (and a note exists), it calls the same `add_rule(..., created_from="learned")` used by `transaction.py`'s manual-edit flow — no separate consent checkbox, since consciously changing the dropdown already *is* the corrective action. **AI infrastructure** ([src/services/ai_client.py](src/services/ai_client.py) + [src/prompts/](src/prompts/), added 2026-07-26 for the "hoạch định tương lai" expansion): the **one** shared entry point for every AI-generated recommendation/explanation across Mốc 1–5 — budget suggestions, goal prioritization, spending-simulation advice, macro-context summaries, and (as of Mốc 5) daily summaries all go through it — explicitly **not** used by `ocr_import.py`'s `analyze_image()`, which is a structurally different task (see above).
- `get_ai_suggestion(cursor, *, task, input_data, response_schema, prompt, model=None, ttl_seconds=...)` **never raises**. It always returns either `{"available": True, "data": <dict>, "cached": bool}` or `{"available": False, "reason": "no_key"|"quota"|"timeout"|"invalid_response"|"network", "data": None}` — the same "sentinel dict, not `None`, not an exception" idiom `risk.py` already uses (`runway_months` returns `{"months": None, ...}`, not `None`), chosen specifically so every template can branch on `{% if ai.available %}` uniformly. `response_schema` is a Pydantic model class — Gemini is forced into matching JSON (`response_mime_type="application/json"`), never parsed from free text, enforcing the standing rule that **AI never computes money**: `input_data` must already contain every number the task needs, computed by plain Python beforehand; the AI only interprets/prioritizes/explains numbers it's handed.
- **Caching**: keyed by `sha256(json.dumps({"task": task, **input_data}, sort_keys=True))` in `ai_cache`, filtered by `expires_at > datetime('now')` (default TTL 6 hours). A cache hit is **not** logged to `ai_calls` (it made no API call, used no tokens — logging it there would misrepresent what that table tracks); a failure is **not** written to `ai_cache` (so it doesn't "poison" the cache and block a retry for the rest of the TTL window). This is also how a "call at most once per day" feature (Mốc 5's daily summary, see "Health-score dashboard" below) falls out for free, with no special-case code: folding `date.today().isoformat()` into that task's `input_data` makes the cache key change once a day on its own.
- **Graceful degradation is structural, not just try/except**: every AI-powered feature is meant to be called from a separate `/api/ai/<task>` JSON endpoint, fetched client-side via `fetch()` **after** the page's own Python-computed numbers have already rendered (a lightweight "Đang phân tích…" placeholder meanwhile) — so a page can never fail or stall because Gemini is slow or unreachable, which matters concretely since PythonAnywhere's free tier may block outbound calls to Gemini's domain entirely (unconfirmed as of Mốc 1 — the first live smoke test against a real deployed host is still owed, see below).
- **Model defaults were deliberately NOT set to the literal names originally requested** (`GEMINI_MODEL` → `gemini-2.5-flash`, `GEMINI_MODEL_HEAVY` → `gemini-2.5-pro`) — `gemini-2.5-flash` is the exact pinned name that already 404'd at runtime with this project's real API key (see `ocr_import.py`'s own history above), so `DEFAULT_MODEL`/`DEFAULT_MODEL_HEAVY` default to the alias family already proven to work instead: `gemini-flash-latest` / `gemini-pro-latest`. The env var names themselves are exactly as requested — only the *fallback value* when they're unset changed. **This needs a live smoke test with a real `GEMINI_API_KEY` before anything is built on top of `GEMINI_MODEL_HEAVY` for Mốc 3/4** — `gemini-pro-latest` has never actually been called successfully yet, unlike the flash alias.
- **A real, easy-to-hit bug found and fixed while wiring this up**: `.env.example` ships several keys with an empty right-hand side (`SECRET_KEY=`, `GEMINI_MODEL=`, ...) so users see the full list of what's configurable. But `os.environ.get("KEY", default)`'s default only fires when the key is **completely absent** from the environment — `python-dotenv` loading `KEY=` from a `.env` file sets it to `""`, which is present-but-empty, so the fallback silently never triggers and code gets an empty string instead of its intended default. This broke `app.secret_key` outright (crashed every login with "the session is unavailable because no secret key was set") and would have silently broken `GEMINI_MODEL`/`GEMINI_MODEL_HEAVY` (Gemini calls with an empty model name) the same way. Fixed everywhere by switching from `os.environ.get(KEY, default)` to `os.environ.get(KEY) or default` — **use this pattern for any future optional env var with a non-empty default**, not the two-argument form, given `.env.example` will keep shipping blank-by-design optional keys.
- Prompt templates live as plain `.md` files in `src/prompts/` (one per task, e.g. `budget_suggestion.md`), loaded and `.format(**context)`'d by the calling route — kept out of Python source specifically so a prompt can be tuned without touching code, per the user's own requirement.

**Balance maintenance**: all writes go through `insert_transaction()` in `transaction.py`, which inserts the row and adjusts `accounts.current_balance` in the same call — there's no trigger. Any new code path that inserts into `transactions` must call this function rather than writing its own INSERT. Symmetrically, `delete_transaction(cursor, transaction_id)` looks up the row's `amount`/`direction`/`account_id` before deleting it and applies the *inverse* balance delta — the only sanctioned way to remove a transaction; it returns `False` (no-op) rather than raising if the id doesn't exist. Used by the web's `/transactions/<id>/delete` (CLI has no delete — it was requested web-only). It also nulls out any `behavior_events.transaction_id` pointing at the row before deleting it (found and fixed 2026-07-26 during a self-review pass) — that FK has no `ON DELETE CASCADE`, so deleting a transaction that had ever been category-edited (which logs a `category_overridden` event) would otherwise fail with a foreign key violation; the event row itself is kept, just detached, since it's still meaningful analytics on its own.

**Shared core vs. CLI vs. web** ([src/transaction.py](src/transaction.py)): the file has two halves, marked by `# ----` section comments. The data-layer half (`get_active_accounts`, `get_categories`, `insert_transaction`, `get_recent_transactions`, `get_transaction_by_id`, `delete_transaction`, `update_transaction_category`, `log_behavior_event`, `get_monthly_totals`, `get_income_sources`, `add_income_source`, `get_budgets`, `set_budget`, `get_period_budgets`, `set_period_budget`, `get_event_templates`, `get_event_template_items`, `create_event_plan`, `add_event_plan_item`, `get_event_plans`, `get_event_plan_items`, `get_rules`, `add_rule`, `delete_rule`, plus the rest of the rules/recurring functions) has no `input()`/`print()` and is imported by both the terminal CLI further down in the same file and by `web_app.py`. The CLI half (`display_accounts`, `add_transaction`, `list_transactions`, `edit_transaction_category_interactive`, `monthly_summary`, `show_risk_report`, `add_rule_interactive`, `list_rules_interactive`, `add_recurring_interactive`, `list_recurring_interactive`, `add_income_source_interactive`, `list_income_sources_interactive`, `set_budget_interactive`, `show_budget_status_interactive`, `list_event_templates_interactive`, `create_event_plan_interactive`, `list_event_plans_interactive`, `main_menu`) is the terminal UI (menu options 1–16), built on top of that data layer — it has no delete for transactions or rules, since delete was requested as a web-only feature. **When changing how a transaction, rule, or recurring item is read or written, change the shared function once** — don't patch `web_app.py`'s SQL and `transaction.py`'s SQL separately, they're meant to stay identical by construction, not by manual sync.

**PWA / "Add to Home Screen" on iPhone**: [src/static/](src/static/) is the **one** static-assets folder in the project (everything else is inlined via `render_template_string`) — it exists only because Flask's built-in static file serving is the simplest way to serve `manifest.json` and the app icons, and `before_request`'s auth check already excluded the `"static"` endpoint from day one (needed since a browser fetches these before any session exists). **Auth on the web form**: single shared password, not per-user login (deliberate — see memory `project_web_form_multiuser_phase`: the goal right now is letting many people log transactions with minimal friction, not tracking who entered what). `APP_PASSWORD` is read from the environment and never hardcoded — the app refuses to start without it. A Flask session cookie (`session["authenticated"]`), valid 30 days, gates every route via a `before_request` hook except `/login`; `/api/*` returns 401 JSON instead of a redirect when unauthenticated. `SECRET_KEY` may also be set via env; if omitted it's a random value generated per-process, meaning all sessions invalidate on every restart — acceptable for this use case, don't "fix" it without being asked. Once deployed somewhere persistent (see below), `SECRET_KEY` should actually be set to a fixed value, otherwise every worker restart on the host logs everyone out. `LOGIN_TEMPLATE`'s password `<input>` has `autocomplete="current-password"` specifically so the browser (Safari Keychain on iPhone) offers to save/autofill it — a small, deliberate friction reduction so re-entering the shared password isn't a recurring tax on every visit.

## Code conventions actually in use

- Function/variable/constant names and comments across `transaction.py`, `seed_data.py`, `init_db.py` are in **English**, per docs/THIET-KE.md Part 6. User-facing text passed to `print()`/`input()` stays in **Vietnamese** — that's the target audience's language, not a convention to migrate away from.
- Money is always stored as integer VND (no decimals).
- Timestamps are stored as `TEXT` via `datetime.now().strftime("%Y-%m-%d %H:%M:%S")` / SQLite `datetime('now')`.
- **`tests/` (added 2026-07-26) is stdlib `unittest` only** — no `pytest`, no fixtures framework, matching the rest of the project's "standard library first" bias. Reserved for genuinely money-math-shaped logic where a hand-computed expected value is worth writing down permanently (`period.py`'s date boundaries, `risk.py`'s retrofitted period metrics, `risk.py`'s health-score functions, and — added 2026-07-27/29 in `tests/test_transaction.py`, the first test file for `transaction.py` itself — `parse_amount_vnd`'s shorthand parsing, `insert_transfer`'s balance/linkage correctness, and the `link_event_plan_to_goal`/`deactivate_goal` wiring fixes) — not a blanket requirement to test every function; most of this codebase is still validated the established way, via a scratchpad-copy-of-`data/finance.db` smoke test before touching real data, not a permanent test file. 130 tests total as of the 2026-07-29 hardening pass (plus `sheet-lite/apps-script/test/test_code.js`'s 13 Node-based tests, separate from this Python suite).
